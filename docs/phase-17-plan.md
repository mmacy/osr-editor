# Phase 17 plan — quests and the advisory battery

Implementation plan for phase 17 of [the osr-editor spec](spec.md). Phase 17 completes the quests panel: the quest builder — activation clause or standing charge, objectives with display names, hidden/reveal, and completion clauses, rewards over the same consequence union, `all`/`any` completion, `concludes_adventure` — quest and objective narrative beats that journal as themselves, the remaining advisory lints (treasure rewards with no accompanying `AwardXP`; key-not-placed, advisory forever), and the audit's quest counting now reading rewards this editor authored. Milestone: author a winnable adventure — a fetch quest whose objective matches the idol's catalog id, activation on entering the dungeon, rewards that grant and award, `concludes_adventure` set — publish it and play it in osr-web to the victory screen.

Phases 15 and 16 carried this phase's foundation deliberately: the osrlib floor is `>=1.6,<2`, the generated types have carried `QuestSpec`, `ObjectiveSpec`, and `TriggerClause` since the floor raise, the re-keying cascade has walked quest sites since phase 15, the flag lint's writer set already counts quest rewards, the forge-mode explanation body already speaks for quests, and the pattern, condition, consequence, and narrative components were built with this phase's parameters designed in. Phase 17 therefore has no floor work, no cascade work, and no component redesign — it authors against a schema and a kit already in hand. Phases 13–14 stay deliberately skipped, exactly as the phase 15 plan records.

Twelve research facts shape this plan more than any others, each verified against the trees rather than recalled:

1. **`QuestSpec`'s shape, and its four parse-time guards.** The model (`osrlib/crawl/quests.py:146`, frozen) is `id` (required, `min_length=1`), `name` (required, `min_length=1` — a quest's name is mandatory, unlike an objective's), `activation` (`TriggerClause | None`, default `None` — the standing charge), `objectives` (a tuple, required, `min_length=1` — an objective-less quest under the `all` rule would be born complete, `quests.py:154-156`), `rewards` (a tuple, default empty), `completion` (`Literal["all", "any"]`, default `"all"`), `concludes_adventure` (default `False`), and `narrative`. `ObjectiveSpec` (`quests.py:93`, frozen) is `id` (required, `min_length=1`), `name` (default `""` — empty means unauthored, falling back to the id everywhere a label shows, `quests.py:99-103`), `when` (`TriggerClause`, required), `hidden` (default `False`), `reveal_when` (`TriggerClause | None`), and `narrative`. Four model validators ride request parse: `_conditions_never_consume` on the clause (`quests.py:79-90` — "a quest condition cannot consume: a quest observes, it does not take"), `_only_a_hidden_objective_reveals` (`quests.py:138-143` — `objective {id!r} is not hidden, so reveal_when would never be read`; a hidden objective with *no* reveal clause is a normal shape that surfaces by completing, `quests.py:105-108`), `_objective_ids_unique` (`quests.py:203-213`, quest-scoped — two quests may share an objective id), and `_rewards_carry_no_source` (`quests.py:215-226`). These and the field constraints are parse-time rejections, not `op_invariant` claims — so the builders enforce them by construction (a name-required create, a disabled last-objective remove, a hidden-uncheck that clears the reveal clause in the same gesture, a client-refused duplicate objective id), with the server's 422 the authority behind each.
2. **`TriggerClause` is the trigger vocabulary re-fielded, so the builders reuse without change.** The clause's field is `pattern`, not `when` (`quests.py:56-58,76`), and its type is the identical seven-member `TriggerPattern` union; `conditions` is the identical three-member gate `ConditionSpec` union with AND semantics (`quests.py:77`, `gates.py:100-103`). The frontend's `PatternBuilder` and `ConditionBuilder` type on exactly those unions and carry no trigger coupling (`pattern-builder.tsx:36-46`, `condition-builder.tsx:39-51`, whose header already names the quest clause as the second `offerConsumes={false}` consumer). `QuestSpec.rewards` is the same closed nine-command `ConsequenceCommand` union as `TriggerSpec.consequences` (`quests.py:198`, `commands.py:2214-2225`), under the same selector rule and the same `_validate_consequence` body — so `ConsequenceBuilder`, `SelectorControl`, and the map door picker arrive free (`consequence-builder.tsx:75-85,247-255,725-735`). The spec's promise that the two surfaces cannot drift is the type system's fact, pinned here by type-level tests.
3. **Quest ids are a separate namespace referenced by nothing in the document — but the save-side orphan is deeper than the trigger case.** `validate_adventure` keeps separate seen-sets (`adventure.py:600,606`) and no document field references a quest id, so a `SetQuest` rename cascades only into the sidecar note key and the delta pointer stays `/quests`. Save-side, though, quest ids are a *closed* domain — the deliberate opposite of `MarkTriggerFired`'s open one: lifecycle state lives in `session.quests` keyed by id, a save replaces that block wholesale on load (`persistence.py:271-275`), and a renamed quest has no state entry at all — the interpreter skips it silently (`interpreter.py:376-378`), lifecycle commands reject `session.command.unknown_quest`, and the view omits it. Objective renames orphan one level down: an `all` quest with a renamed objective can never complete from an old save (`interpreter.py:425-426`). The guide states this as osrlib's posture; the editor forks no repair.
4. **Order is semantics for quests twice over, and objective order matters inside each.** Quests seed in document order (`session.py:376-385`), the interpreter walks all triggers first and then all quests, each in document order (`interpreter.py:294-318`; stamps proven `trigger:… , quest:…` in `tests/test_interpreter.py:584-589`), and the player view ships authored order (`views.py:386-393`). Within a quest, objectives seed, walk, list, and validate in authored order, and the `any` rule completes on the first authored objective whose clause lands in the walk (`interpreter.py:391-416,420-427`). `MoveQuest` is therefore `MoveTrigger`'s exact mirror; objective and reward reorder need no op — they live inside the spec, and the whole-value `SetQuest` grain carries their order, the consequence-list precedent.
5. **The lifecycle beats and what "journal as themselves" means in code.** Four moments read four beats: quest activation reads `QuestSpec.narrative.offer` (`session.py:1157`), objective reveal reads `ObjectiveSpec.narrative.offer` (`session.py:1183`), objective completion reads `ObjectiveSpec.narrative.progress` (`session.py:1213`), quest completion reads `QuestSpec.narrative.completion` (`session.py:1237`, reused by `AdventureCompletedEvent` at `1247`). Each beat is appended to the journal as its own text and rides the lifecycle event's `narrative` field at player visibility — no separate journal event fires, because "the quest's own lifecycle event *is* this beat's event" (`session.py:1136-1146`) — and the quest layer never reads `NarrativeBlock.journal`. So the quest and objective narrative editors carry beats `offer`/`completion` and `offer`/`progress` and no journal voice; a foreign block's `journal` or `fired` text is the unread-beat warning's case. Two honest wrinkles for help text: a standing charge (no activation) seeds active with no activation moment, so its offer never journals but still ships in the player's quest view (`views.py:413`, `tests/test_quests.py:427-432`); and reveal is the *only* reader of an objective's offer, so a born-visible objective's offer beat is read at no lifecycle moment. Display names fall back `objective.name or objective.id` at all three sites (`views.py:405`, `session.py:1190,1220`), and events carry `quest_name` resolved at emission.
6. **`concludes_adventure` flips to victory before the first reward issues.** The only entrance to `SessionMode.VICTORY` is `_handle_complete_quest` (`session.py:1240-1247`); the interpreter issues `CompleteQuest` and *then* the rewards (`interpreter.py:405-416`), so on a concluding quest the session is already terminal when rewards execute: `SpawnMonsters`, `SpawnNpcParty`, and `PlaceParty` drop with `session.command.wrong_mode` notes while grants, awards, and flags land (`interpreter.py:243-245`, `tests/test_interpreter.py:710-728`). Nothing caps concluding quests — the guide carries the author-it-once convention; a second one completing merely journals — and completing any quest from a terminal mode journals without a second `AdventureCompletedEvent` (`tests/test_quests.py:746-756`).
7. **The engine's XP-valuation rule, exactly — the unpriced-rewards lint's whole justification.** `party_valuation_cp` (`session.py:825-838`) counts coins at face value and valuables at `value_gp`; "Magic items and mundane equipment count zero — magical treasure grants no XP per RAW, and mundane-gear salvage sits below the simulation floor by design." The return award prices the valuation *delta* (`award_adventure_xp`, `session.py:844-886`); `AwardXP` is the direct instrument. So a `GrantItem` reward never prices anywhere; a `GrantCoins` on a concluding quest lands after victory, where no return award ever runs (fact 6); and granted coins on a non-concluding quest price themselves at the return award and need no flag — the spec's three cases, each grounded in one code site.
8. **The quest-owned validation grammar is enumerable, one level deeper than the trigger grammar.** Every quest-owned line is built from four site prefixes: `quest {id!r}` (`adventure.py:447`), the objective insertion ` objective {oid!r}` (`:453`), the reveal suffix ` reveal` (`:461`), and the reward site `{owner}: reward {position}` (`:469`), plus the uniqueness line `quest {id!r}: id is not unique` (`:609`). The tails are byte-identical to the trigger tails after the site prefix — the same `_validate_clause` and `_validate_consequence` bodies serve both owners (`adventure.py:316-362,365-413`, their docstrings naming both) — six clause tails (unknown dungeon+level, unknown area, unknown dungeon, unknown item, unknown monster, condition unknown item) and six reward tails (the selector violation, unknown item, unknown monster, unknown dungeon+level, no door, out of bounds). `TownEnteredPattern` and `FlagSetPattern` yield no pattern check, `SetFlag`/`SpawnNpcParty`/`AdvanceTime` no reward check, and a town `PlaceParty` returns unchecked — flag keys and effect kinds are open domains. Enumeration confirmation must therefore extend one level down: quest ids confirm by rendering, and at objective sites the *confirmed quest's* objective ids confirm too, both exactly as osrlib reprs them.
9. **The backend machine already runs quests; this phase adds no cascade, writer-set, or forge-section code.** `_rewrite_authored_layer` has walked a quest's activation, each objective's `when` and `reveal_when`, and its rewards since phase 15 (`documents.py:1551-1622`, proven by `test_authored_cascade.py`, whose docstring already promises the committed fixtures grow quest content with this phase). `_flag_writers` counts quest-reward `SetFlag`s (`lint.py:296-299`), and the flag lint's quest readers sit visible at `address=None` with a docstring naming phase 17 (`lint.py:317-320,344-359`). `ForgeQuestsBody` already explains for quests (`quests-section.tsx:180-215`), `NavTarget` carries the `quests` variant (`address.ts:29-32`), `BEAT_LABELS` already labels Offer, Progress, and Completion (`narrative.ts:19-27`), and the generated types carry the whole quest schema (`api.ts:4769,4231,6651`) — only the four ops are missing from the 36-member `AnyEditOp`.
10. **The key-not-placed walks all exist; `lint.py` lacks only imports.** Which caches hold an item: the `feature.item_ids` walk over area and level features (`documents.py:1432-1477`). Which consequences grant one: the `GrantItem` closure the item-rename cascade already applies to trigger consequences and quest rewards alike (`documents.py:1719-1721`). Which gates require one: the `HasItemCondition` walks over door and transition `requires` (`documents.py:1425-1429,1461-1476`). Bundled-versus-shipped resolution: `_shipped_item_ids` (`documents.py:1294-1304`, exactly the seen-set osrlib's `_effective_equipment` seeds). `lint.py` today imports none of `HasItemCondition`, `GrantItem`, `GrantCoins`, `AwardXP`, or `item_address` (`lint.py:48-54`) — the phase 16 `edge_address` precedent, repeated.
11. **The component kit arrives free, but the two list wrappers are private.** `ConditionList` and `ConsequenceList` — the add/remove/edit condition rows and the ordered consequence list with per-row reorder — are module-private in `quests-section.tsx` (`:515-605,:607-723`); the quest builder needs both (clause conditions; rewards), so they extract into shared components rather than duplicating — the greenfield rule. Everything else is exported and uncoupled: `PatternBuilder`, `ConditionBuilder`, `ConsequenceBuilder` with `SelectorControl` and the door picker inside it, `MiniLevelPicker`, `NarrativeBlockEditor`, `useCommittedField`, and `trigger-builders.ts`' summary functions (`patternSummary`, `consequenceSummary`) that the quest summaries ride.
12. **osr-web proves the milestone's played half end to end, API-driven.** Completing a concluding quest yields `view.mode == "victory"` through direct endpoint calls (`osr-web tests/test_quest_log.py:296-302`), the victory screen renders from that mode (`static/app.js:666,2816,3466-3525`), the quest view contract carries id, name, the offer beat, speaker, and objectives, and upload-time content validation covers quest references (`server/content.py:213`). The transcript pattern from phases 15 and 16 stands unchanged.

## Work items

### 1. The quest ops

Four new frozen ops in `ops.py`, adventure-scoped, the trigger quartet's shape verbatim, embedding the osrlib model whole:

- **`AddQuest`** — `quest: QuestSpec`. Appends to `Adventure.quests`: authored order is seeding and walk order, and appending is the only insertion (a misplaced quest moves after the fact).
- **`SetQuest`** — `quest_id: str`, `quest: QuestSpec`: whole-value replacement, first match among foreign duplicates. A differing `quest.id` is a rename — no document site references a quest id (research fact 3), so the rename cascades only into the sidecar: `_remap_rules` grows the `quest:<old>` → `quest:<new>` rule, and its "six re-keying ops" docstring is corrected to seven in the same commit, the falsified-docstring convention. Delta pointer `/quests` in every case, rename included. Objective-scoped edits — add, remove, rename, reorder, every field — ride this op whole; no objective op exists, the consequence-list grain.
- **`MoveQuest`** — `quest_id: str`, `index: int` (`ge=0`): splice out, insert at `index`. Out-of-range rejects as `op_invariant` naming the valid range ("the document's quests occupy positions 0 through {last}", the `MoveTrigger` wording over quests); a same-position move applies as a harmless no-change batch, and the UI never posts one.
- **`RemoveQuest`** — `quest_id: str`, first match. Nothing in the document references a quest id, so removal dangles nothing; the save-side orphan is osrlib's own posture (fact 3), noted in the guide, and the UI's two-step row confirm is the only guard.
- The invariant, `_require_quest_id_free` beside its trigger sibling and equally small: only the rest of `Adventure.quests` (trigger ids are a separate namespace and impose nothing), new or changed ids only — the carry-through rule: a foreign document's duplicate ids open, edit, and navigate, resolved first-match, flagged by the `quest_id_not_unique` classification, never locked. Empty ids and empty names need no invariant: both carry `min_length=1` and reject at request parse.
- Application: `_resolve_quest` and the four `_apply_*_quest` helpers rebuilding `Adventure.model_copy(update={"quests": ...})`, dispatched beside the trigger branches. The parse-time guards arrive free and are proven by test: a consuming clause condition, a source-carrying reward, duplicate objective ids, a reveal clause on a visible objective, zero objectives, and an empty quest name all reject at request parse — the gated-slide precedent extended to the quest shapes.

### 2. Forge blocking

- `_BLOCKED_MESSAGES` grows four entries sharing one message in the trigger wording's shape: `_QUEST_BLOCKED = "quests have no override kind — the overrides vocabulary has no authored-layer surface"`. `_blocked_address` grows the matching branches: `quest_address(op.quest.id)` for `AddQuest`, `quest_address(op.quest_id)` for the other three. Whole-op blocks only; `translate_batch`'s closing assertion keeps enforcing that every new op took the blocked path.

An unconsumed constant would be exactly the dead accommodation code the greenfield rules forbid; the server's 422 is the whole story for any batch that arrives. `ForgeQuestsBody` needs only its future tense retired (item 7).

### 3. Addresses and diagnostics

- `addresses.py` grows `quest_address(quest_id) -> "quest:<id>"`, a top-level segment beside `trigger:<id>`; the bare `quests` scope joins the coarse degrade targets.
- `diagnostics.py` grows the `_QUEST_SHAPES` table — thirteen codes mirroring the trigger thirteen: `quest_id_not_unique`; `quest_pattern_unknown_level`, `quest_pattern_unknown_area`, `quest_pattern_unknown_dungeon`, `quest_pattern_unknown_item`, `quest_pattern_unknown_monster`; `quest_condition_unknown_item`; `quest_selector_violation`, `quest_reward_unknown_item`, `quest_reward_unknown_monster`, `quest_reward_unknown_level`, `quest_reward_no_door`, `quest_reward_out_of_bounds`. Classification extends the enumeration-confirmation discipline one level down (research fact 8): for each quest the classifier renders the site prefixes osrlib builds — `quest {id!r}: ` for activation clauses, rewards, and the uniqueness line, and per objective of that quest `quest {id!r} objective {oid!r}: ` and `quest {id!r} objective {oid!r} reveal: ` — exactly as osrlib reprs the ids, and full-matches the remainder against the tails. Both the quest id and, where the site carries one, the objective id must confirm by enumeration; a site's objective id confirms only against the confirmed quest's own objectives. The address is `quest:<id>` in every case — the quest detail editor owns its objectives, so no finer address exists to lie about. A whole-line generic shape that matches with no confirmed ids degrades to the bare `quests` scope — always true, never a lie; anything else stays `validation_unclassified` verbatim. The dangling ids inside the tails stay message text. The phase 16 pin (`test_quest_error_strings_still_land_unclassified_verbatim`) inverts, and the module comment "until phase 17 grows their grammar" retires.
- `address.ts`: the `quests` scope resolves to the section; `quest:<id>` resolves to `{kind: 'quests', questId}` with the quest open, refusing (null) when no such quest exists — the `trigger:<id>` posture exactly. `NavTarget`'s quests variant grows `questId?` beside `triggerId?`; an address names one surface, so at most one is ever set. The diagnostics panel and map markers need no changes; quest findings are top-level addresses and draw no marker.

### 4. The advisory battery completes

Two new checks in `lint.py`, appended after `trigger_spawn_collision` in the vocabulary's order, each a `SEVERITY` entry at `"warning"` — advisory by construction, never escalating, never gating — plus the address upgrade phase 16 left signposted:

- **`quest_reward_unpriced`** — treasure rewards the award machinery will never price, with no accompanying `AwardXP`. Per quest: a reward tuple containing a never-priced grant — any `GrantItem` (granted items always value at zero, research fact 7), or a `GrantCoins` when `concludes_adventure` is set (the grant lands after victory, where no return-to-town award ever runs, fact 6) — with no `AwardXP` among the same quest's rewards yields one finding, addressed `quest:<id>`, its message naming the engine's rule. Granted coins on a non-concluding quest price themselves at the return award and stay silent; an `AwardXP` anywhere in the tuple silences the quest. The check reads quest rewards alone, by the spec's own vocabulary — "rewards" and "accompanying" are quest words, and a trigger's `GrantItem` is a key or a tool, not a payment: flagging it would false-positive on the exact lever-and-key wiring phase 16 exists for.
- **`key_not_placed`** — a `has_item` gate on a bundled item that no cache holds and no consequence grants. Sites: every door `requires` and every transition `requires` whose condition is a `HasItemCondition` naming a bundled id — shipped ids are purchasable and never flagged, with `_shipped_item_ids` the resolver; a dangling id is the validation tier's finding, not this one's. Satisfiers: any area- or level-feature `item_ids` naming the id, and any `GrantItem` in trigger consequences or quest rewards. One finding per gate site, addressed to the door's edge or the transition's cell (the flag lint's one-per-reading-site posture); a consuming toll flags like any other gate — an unplaceable toll is the same authoring mistake. Advisory forever, because trigger-granted items and random treasure make the general problem undecidable. `lint.py` grows the imports it lacks (`HasItemCondition`, `GrantItem`, `GrantCoins`, `AwardXP`, `item_address` is not needed — the addresses are carrier addresses), the phase 16 precedent.
- **The flag lint's quest readers get their addresses**: the `address=None` sites (`lint.py:344-359`) now address `quest:<id>` of the owning quest — activation, objective completion, and reveal clauses alike — and the "until phase 17" sentences in `lint.py` retire.
- The parity suite's docstring exclusion list grows the two ids; `SHARED_CHECKS` is untouched. The perf pin re-proves the full pass with five advisory sweeps. The reachability lint stays gate-blind — the unsatisfiable-gate case now has its advisory home, exactly as the spec assigned it.
