# Phase 9 plan — documentation and release

Implementation plan for phase 9 of [the osr-editor spec](spec.md), the roadmap's final phase: the docs site (mkdocs-material), the release-grade README, the packaging audit, tag-driven trusted publishing, and the PyPI release as `osr-editor` 0.1.0 (Development Status :: 4 — Beta), matching the family's release engineering. The milestone follows osr-forge's phase 4 precedent exactly: the phase is not "ready to release" but *released* — `uv tool install osr-editor` in a clean environment on a machine with no node toolchain starts the editor and serves the full UI, the docs site is live, and the GitHub release carries the changelog. Unlike every prior phase, phase 9 adds no editor behavior; its deliverables are the pipeline, the site, and the published artifact, so the "working, tested, documented software" bar lands on the release machinery itself — the audit and smoke scripts are the phase's tests.

Nine research facts shape this plan more than any others:

1. **osr-forge 0.1.0 is on PyPI (published 2026-07-21), and the git pin's premise is dead.** `pyproject.toml:71-73`'s `[tool.uv.sources]` entry and its "osr-forge has no PyPI release yet" comment are stale; worse, `uv.lock:319` pins commit `4b43fa5` — one commit *before* forge's release commit `7e81dc3` — so the locked build self-reports 0.1.0 while not being the audited PyPI artifact. osrlib is at 1.3.0 on PyPI, ahead of the `>=1.3,<2` pin. Deleting the sources block and re-locking makes both runtime dependencies published PyPI ranges — the family's "published builds pin PyPI ranges" posture, and the last structural blocker to this release.
2. **`uv_build` packages the tree, not the git index — verified empirically (2026-07-24).** With the frontend built, `uv build` ships `osreditor/static/` (gitignored) in both the wheel and the sdist, so phase 0's decision — no build hooks, the Vite build is a release-CI step — works with zero build-backend change. The same experiment shipped a stray `.DS_Store` in the sdist: `.gitignore` protects nothing at packaging time, so junk exclusion and the audit's sweep are load-bearing, not hygiene theater.
3. **The family's `release.yml` shape is proven twice and structurally identical**, and this plan copies it rather than redesigning it: a `check-tag` gate (stdlib `tomllib`, tag must equal `v` + pyproject version), the standing CI gate duplicated by hand because a tag push triggers no CI run (both siblings document rejecting a `workflow_call` refactor), a strict docs build, one `build` job whose artifact every downstream job consumes ("what publishes is byte-for-byte what was audited"), fresh-venv install smokes on both OSes, trusted publishing under `environment: pypi` with `id-token: write` and no checkout, and a GitHub release awk-extracted from the changelog section that fails when the section is missing. Recovery rule: any failure before publish leaves PyPI untouched — delete the tag, fix, re-tag; after publish, that version's filenames are burned.
4. **The dist audits are stdlib-only scripts run against artifacts, never the repository tree**: exactly one wheel and one sdist; filename and `py3-none-any` tag checks; the full `src/` module tree present in the wheel; named must-haves asserted independently of the tree listing ("deleting it from src/ must fail the audit, not shrink expectations"); `dist-info/licenses/LICENSE`; METADATA equality against `[project]` for Name, Version, License-Expression, and Requires-Python; no `License ::` classifier beside the SPDX expression (PEP 639); and a forbidden-member sweep (repository directories, bytecode, and — forge's licensing fence — fixture JSON and page images).
5. **The install smokes prove resolution, version, and behavior — and the editor's behavior check must fetch `/`.** `app.py:1722` mounts static only when the directory exists, precisely so a dev backend boots without a built frontend — which means a static-less wheel boots healthy, answers `/api/status`, and 404s the UI. Only requesting `/` from the installed console script catches the one packaging failure this phase exists to prevent.
6. **Docs deploy is Pages-from-workflow, not a gh-pages branch**: `mkdocs build --strict` in CI, `upload-pages-artifact` on `main` pushes, `deploy-pages@v4` under the `github-pages` environment; the one-time repository setup is flipping the Pages source to "GitHub Actions". Both siblings exclude design docs from the published site via `exclude_docs` (`spec.md`, `phase-*-plan.md`), and both defer versioned docs with the same named trigger: the first post-1.0 release whose published docs must describe behavior different from `main` adopts mike in that release's own plan.
7. **osrlib pins `mkdocs-gen-files` and `mkdocs-literate-nav` exactly because their next releases depend on `properdocs`**, an unvetted mkdocs fork that ships an import hook redirecting all `mkdocs.*` imports to itself. The editor's site needs neither plugin — its reference surface is one seam, not a generated per-module tree — so the site adopts a hand-written nav and avoids the hazard entirely instead of inheriting the pins.
8. **Version discipline is already in place and stays**: the version lives in `pyproject.toml` alone, `_editor_version()` reads installed metadata at runtime (`app.py:1733`), and no `__version__` symbol exists (osrlib rejected one explicitly). The bump procedure is: edit the version, `uv lock`, nothing else. The changelog is Keep a Changelog; the release renames `[Unreleased]` to the version and date, which is exactly the heading the awk extraction requires. osrlib's own link-reference block drifted unmaintained after 1.3.0 — so this repo's release commit writes the reference block correctly and the runbook names maintaining it as part of every release.
9. **The PyPI name held**: `osr-editor` returned 404 at phase 0 planning and again at phase 0 PR time (2026-07-18). The check is re-run at this plan's PR time and at the implementation PR, recorded as amendments, with `osredit` still the ceremony-free fallback.

## Scope

In scope:

- Dropping the stale osr-forge git source and re-locking against PyPI (fact 1)
- Packaging metadata for release: version 0.1.0, `Development Status :: 4 - Beta`, the `Documentation` project URL, junk exclusion at the build backend
- The dist audit (`scripts/release/check_dist.py`) and install smoke (`scripts/release/install_smoke.py`), plus the documented local dry run
- `release.yml`: the full tag-driven chain through trusted publishing and the GitHub release
- The docs site: mkdocs-material configuration, the content set below, the third-party importer guide (phase 8's named deferral), the licensing page, and the CI docs-build and Pages-deploy jobs
- The README rewritten for a released package
- The `AGENTS.md` releasing runbook, replacing the placeholder sentence with the family procedure
- CHANGELOG release shaping: the phase 9 bullet, the `[0.1.0]` section cut, and the link-reference block
- The release act itself — the owner's ordered checklist, executed to the end, because the milestone is *released*

Out of scope (each with where it goes): versioned documentation — deferred with the siblings' exact adoption trigger, recorded in the runbook. A TestPyPI rehearsal, a PR-time build-and-audit job, a `__version__` re-export, and Dependabot/SHA-pinning — all four rejected by osrlib's phase 8 with rationale this repo inherits rather than relitigates; the local dry run and the release gate are the rehearsal. A published REST API reference — the `/api` surface is the bundled frontend's private contract, not a public one; documenting it would freeze what the spec deliberately left free, and it waits for the hosted-deployment future that would make it public. Screenshots — the 0.1.0 site is prose-only: the quickstart puts the reader in the real editor in two commands, a stale screenshot of a living UI is a lie with a caption, and the revisit trigger is named (a 1.0 site, or evidence readers bounce without them); if that trigger fires, Playwright already automates the capture. A docs changelog page — discovery is the PyPI `Changelog` URL and the GitHub release notes, osrlib's decision. `mkdocs-gen-files`/`mkdocs-literate-nav` (fact 7). New editor behavior of any kind — the app surface is frozen for the phase; the one sanctioned code change is packaging-adjacent (the dependency posture), and the fixture and golden suites prove the freeze. Registries beyond PyPI — `uv tool install` and `pipx` are install paths over the same wheel, not new pipelines.

## Work items

### 1. The dependency posture

Delete the `[tool.uv.sources]` block and its stale comment from `pyproject.toml`; run `uv lock`; commit the lock that resolves `osr-forge==0.1.0` from `registry = "https://pypi.org/simple"`. The declared range `osr-forge>=0.1,<0.2` is already correct and does not change. The standing CI (`uv sync --locked` on both OSes) is the proof. Local development against unreleased sibling surface stays what the README documents: an editable path override for the duration, reverted before merge — never a manifest entry.

### 2. Packaging metadata and hygiene

`version = "0.1.0"`; `Development Status :: 4 - Beta` replacing `3 - Alpha` (the spec's named classifier); `Documentation = "https://mmacy.github.io/osr-editor/"` joining `[project.urls]`. `[tool.uv.build-backend]` grows junk exclusion (`source-exclude`/`wheel-exclude` covering `.DS_Store` and kin) so fact 2's leak is fixed at the source *and* swept by the audit — belt and suspenders, because the tree is what ships and the tree is not the git index. The wheel filename normalizes to `osr_editor-0.1.0-py3-none-any.whl` (PEP 427 underscore), which the audit and smoke glob for.

### 3. The dist audit

`scripts/release/check_dist.py` — stdlib-only, run as `python3 scripts/release/check_dist.py dist X.Y.Z`, adapted from the siblings' scripts with the editor's specifics. It accumulates every failure before exiting, and checks: exactly one wheel and one sdist; wheel filename and `Tag: py3-none-any` (only); every file under `src/osreditor/` present in the wheel; named must-haves asserted independently of the tree listing — `osreditor/py.typed` and `osreditor/static/index.html`; **the static freshness check** — parse `index.html` for its hashed `assets/` references and require each referenced file present in the wheel, which catches both the never-built and the stale-mixed static tree, the two failure shapes a wrong build order produces; `dist-info/licenses/LICENSE`; METADATA equality against `[project]` for Name, Version, License-Expression (`MIT`), and Requires-Python; no `License ::` classifier (PEP 639); and the forbidden-member sweep over both artifacts — `tests/`, `docs/`, `scripts/`, `frontend/`, `site/`, `test-results/`, `node_modules/`, `__pycache__/` directories, `.pyc` and `.DS_Store` members, fixture-named JSON (forge's licensing-fence sweep, inherited: the editor ships no game content and no committed fixture may ride along), and any path segment ending `.osr` or `.forge` (a scratch project misplaced into `src/` would ship, because the tree is what ships). The sdist checks mirror forge's: name, `pyproject.toml`/`README.md`/`LICENSE`, the full `src/osreditor/` tree **including `static/index.html`** — the sdist is the wheel's build input and `frontend/` is deliberately not in it, so the built static is a shipped build input exactly the way osrlib's generated data files are, and a wheel built from the sdist needs no node.

### 4. The install smoke

`scripts/release/install_smoke.py` — stdlib-only, run with the fresh venv's interpreter as `smoke-venv/bin/python scripts/release/install_smoke.py X.Y.Z`, importing nothing from `tests/`. Checks, in order: `osreditor` resolves under `site-packages` (not a shadowing checkout); `importlib.metadata.version("osr-editor")` equals the expected version; the `osreditor.importers` entry-point group lists exactly `project` and `watabou-opd` (the seam's registration survived packaging); the dependencies resolved as published artifacts — `import osrforge` succeeds and osrlib's `load_monsters()` catalog is non-empty, forge's own smoke pattern. Then the behavior check (fact 5): bind port 0 to learn a free port, launch the installed **console script** (`osr-editor --no-browser --port N`) as a subprocess — the script itself is under test, not just the package — poll `/api/status` with `urllib.request` until it answers, assert `editor_version` equals the expected version and `engine_version`/`schema_version` are present, then GET `/` and assert an HTML document that references the built Vite assets, proving the wheel carries and serves the UI; terminate the subprocess and fail loudly if it exited early. Loopback only, no browser, no network beyond localhost.

### 5. release.yml

Mirrors the siblings job-for-job, with the editor's own standing gate substituted. Trigger `push: tags: ["v*"]`, top-level `permissions: contents: read`. Jobs: **check-tag** (stdlib `tomllib`, `$GITHUB_REF_NAME` must equal `v` + version — a tag on an unbumped tree dies before any matrix spins up); **the standing gate duplicated by hand** — the backend matrix (ubuntu + macos: `uv sync --locked`, ruff format/check, pyright, pytest), the frontend job (prettier, eslint, `tsc -b`, vitest, build), the types drift gate, and the e2e job, each copied from `ci.yml` with the siblings' "keep in sync by hand" comment, because a tag push triggers no CI run and the release re-proves the tree — the editor's gate is four jobs where the siblings have one, and the e2e job stays in because a release that skips the flagship loops' smoke is weaker than the PRs that built it; **docs** (`uv run mkdocs build --strict`); **build** — needs all gates, and its ordering is the whole packaging story: setup-node, `npm ci`, `npm run build` (populating `src/osreditor/static/`), then `uv build`, then `check_dist.py`, then upload the `dist` artifact that every downstream job consumes; **install-smoke** on both OSes from that artifact (`uv venv --python 3.14`, install the wheel by path, run the smoke); **publish** — needs install-smoke, `environment: {name: pypi, url: https://pypi.org/project/osr-editor/}`, `permissions: id-token: write`, `pypa/gh-action-pypi-publish@release/v1`, no checkout, no credentials anywhere in the repository; **release** — awk-extract the tagged version's CHANGELOG section, fail if empty, `gh release create` with the notes.

### 6. The docs site

`mkdocs.yml`: material theme with the family's light/dark palette toggle, `site_url: https://mmacy.github.io/osr-editor/`, `strict: true`, the full `validation:` block, `watch: [src]`, `exclude_docs` covering `spec.md`, `phase-*-plan.md`, and `backlog.md` (design docs stay in the repo, off the site). Plugins: `search`, `autorefs`, and `mkdocstrings` (google style, `paths: [src]`, inventories for python, pydantic, **and both siblings' `objects.inv`** so seam docs cross-link osrlib's spatial types and forge's contracts). Markdown extensions match osrlib's, including `pymdownx.snippets` with `check_paths: true`. No `gen-files`, no `literate-nav` (fact 7): the nav is hand-written.

Nav and content — the README's per-surface prose (currently the deepest user documentation the project has) seeds the guides, then the README slims to a map (item 7):

- **Home** — what osr-editor is, the family it belongs to, where to start.
- **Getting started** — installation (`uv tool install osr-editor`, `pipx install osr-editor`, or `pip install osr-editor`; Python ≥ 3.14; no node, ever, for users) and the quickstart (launch, the home screen, first adventure, first room, export).
- **Guides** — projects (the two project types, always-saved, undo, the sidecar, git-friendly documents); the map editor; stocking and keyed content; the monster editor; forge-backed review; converting a PDF (including provider configuration and the no-secrets-on-disk rule); authoring aids; import, export, and publish.
- **Reference** — the CLI and configuration (flags, port, `platformdirs` paths); **writing a geometry importer** — phase 8's named deferral, closed: the `GeometryImporter` protocol contract (bounded `sniff`, `load`'s `ImportSourceInvalidError` failure mode), the payload's semantics (an absent edge is a wall, `entrance` optional, dangling transition targets legal-but-linted), registration through the `osreditor.importers` entry-point group with a complete third-party `pyproject.toml` example, the judgment-call `notes` contract, and mkdocstrings directives over the seam's exports. The guide's example importer is excerpted via `pymdownx.snippets` from real, tested source — `tests/test_importers.py`'s synthetic importer grows named snippet sections (or a dedicated tested example lands beside it if the synthetic one is too skeletal to teach from), so the documented code cannot drift from code that passes.
- **Licensing** — MIT code, no game content in this package (osrlib carries the OGL data), user modules stay the user's.

A `docs` dependency group (PEP 735: mkdocs, mkdocs-material, mkdocstrings[python]) joins `[dependency-groups]`, included from `dev` — contributor tooling, not published extras, osrlib's pattern. `ci.yml` grows the **docs** job (`mkdocs build --strict`, upload the Pages artifact on `main` pushes) and **deploy-docs** (`actions/deploy-pages@v4`, `github-pages` environment) — Pages-from-workflow, no gh-pages branch ever. All docs prose follows the repo's voice and sentence-case rule.

### 7. The README for a released package

The status paragraph flips from "pre-alpha, phases 0–8 in place" to released: install from PyPI, learn at the docs site, with the per-surface deep dives migrating into the guides and the README keeping a tight product map that links out — the siblings' posture, where the README sells and the site teaches. Installation becomes the three-command story (`uv tool install osr-editor` first — it's an application with a console script, and that's the modern path — then pipx, then pip); the quickstart collapses to install-and-run, and the current two-toolchain build-first quickstart moves under Development, which keeps the full local gauntlet verbatim. Every link goes absolute — PyPI renders the README far from the repo, so `docs/spec.md`-style relative links break there. Licensing keeps its current three sentences.

### 8. The runbook and the changelog

`AGENTS.md`'s releasing section replaces its placeholder sentence with the family runbook: the version lives in `pyproject.toml` alone and the bump is edit-version-then-`uv lock`-then-nothing-else; changelog discipline as already practiced; a release is an annotated `vX.Y.Z` tag on the merge commit and `release.yml` does the rest; the local dry run **starts with the frontend build** (`npm ci && npm run build`, then `uv build`, then the audit, then the fresh-venv smoke) because a dry run that skips it audits a stale tree; the recovery rule including burned filenames; the versioned-docs deferral with the family's adoption trigger verbatim; and the link-reference block as part of every release cut (fact 8's drift lesson). The one-time setup — the PyPI pending publisher (project `osr-editor`, owner `mmacy`, repository `osr-editor`, workflow `release.yml`, environment `pypi`), the repo's `pypi` environment, and the Pages source flip to "GitHub Actions" — is recorded as created during this release, not as pre-existing state: forge's provenance correction is the cautionary precedent, and this repo writes it honestly the first time. The CHANGELOG's release commit renames `[Unreleased]` to `[0.1.0] - <date>`, adds the phase 9 bullet (docs site, packaging audit, release engineering — the last entry, since the release itself is the phase's behavior change), leaves an empty `[Unreleased]` above, and writes the reference block (`[Unreleased]` comparing `v0.1.0...HEAD`, `[0.1.0]` pointing at the release tag) — exactly the shape the awk extraction and Keep a Changelog both want.

### 9. The release act

After the implementation PR merges, the owner executes, in order: (1) on pypi.org, add the pending trusted publisher and create the repo's `pypi` environment; confirm the Pages source is "GitHub Actions"; (2) `git tag -a v0.1.0 -m "osr-editor 0.1.0"` on the merge commit, push the tag; (3) watch `release.yml` through publish and release — on any failure before publish, delete the tag, fix on a branch, re-tag; after a successful publish, a failed release job is recoverable by hand and the publication stands; (4) verify: the PyPI page renders the README with working links, `uv tool install osr-editor` in a clean environment starts the editor and serves the UI, the docs site is live and its install instructions are now true, and the GitHub release carries the 0.1.0 notes. The phase is complete when this checklist has run to the end.

## Sequencing

1. The dependency posture: drop the git source, re-lock, standing CI green — the smallest PR-able unit and everything else's foundation.
2. Packaging metadata and hygiene: 0.1.0, Beta, the Documentation URL, junk exclusion.
3. The audit and smoke scripts, proven by the local dry run — including one deliberate failure: run the audit against a build made *without* the frontend step once, and see it fail on the static must-have, so the guard is demonstrated rather than assumed.
4. `release.yml`, mirroring the gates.
5. The docs site: mkdocs configuration, the content set, the importer guide with its tested excerpts, the CI docs and deploy jobs.
6. The README rewrite, the AGENTS.md runbook, the CHANGELOG shaping.
7. PR-time PyPI name re-verification, recorded as an amendment (fact 9).
8. Post-merge: the release act (work item 9), run to the end.

## Definition of done

- The full gauntlet is green on both toolchains with zero network in CI, now including `mkdocs build --strict` and the Pages deploy on `main`.
- The local dry run passes end to end — frontend build, `uv build`, audit clean, fresh-venv smoke boots the console script and serves the UI from the wheel — and the audit has been *seen* to fail on a static-less build during development.
- The dist is machine-checked clean: no repository directories, no bytecode, no junk, no fixture JSON, no game content; the wheel and sdist both carry the built frontend; METADATA matches `[project]` under PEP 639.
- Both runtime dependencies resolve from PyPI in the committed lock; no `[tool.uv.sources]` entry survives.
- The docs site builds strict, deploys from `main`, excludes the design docs, and closes phase 8's deferral: the importer guide exists, its example code is excerpted from tested source, and a third party could ship a converter from the guide alone.
- The README is true after release: install commands work as written, links are absolute, and depth lives on the site.
- The runbook in `AGENTS.md` is the complete release procedure, and the one-time setup is recorded with honest provenance.
- The release act has run to the end: `osr-editor` 0.1.0 live on PyPI as `Development Status :: 4 - Beta`, installed-and-boots verified in a clean environment, docs live, GitHub release cut — *released*, not ready-to-release.
