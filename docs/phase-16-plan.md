# Phase 16 plan — triggers

Implementation plan for phase 16 of [the osr-editor spec](spec.md). Phase 16 brings the quests panel into the nav with its trigger surface first: the trigger list preserving document order with reorder ops, the pattern builder over all seven kinds, trigger conditions (consume-free by construction), the consequence builder over the closed nine-command union with selector-only recipients, the fired and journal voices in the narrative editor, area and level triggers placed from the map the way transitions are with glyphs at their addresses, `SetDoorState` consequences picking their door on the map, and the first advisory lints — flag reads with no writer, trigger cycles, collision-prone trigger/encounter pairings. Milestone: the lever-opens-portcullis pairing — a flag-setting lever trigger and a flag-gated door — authored from the map, published, and played in osr-web.

Phase 15 carried this phase's foundation deliberately: the osrlib floor is `>=1.6,<2` with the source pin retired, every fixture is re-stamped at schema 3, the generated types already carry the whole trigger schema, and the shared components were built with this phase's parameters designed in. Phase 16 therefore has no floor work, no fixture re-stamp, and no shared-component refactor — it authors against a schema and a component kit that are already in hand. Phases 13–14 stay deliberately skipped, exactly as the phase 15 plan records.

Ten research facts shape this plan more than any others, each verified against the trees rather than recalled:

1. **`TriggerSpec`'s shape, and its two parse-time guards.** The model (`osrlib/crawl/triggers.py:191`, frozen) is `id` (required, `min_length=1`), `when` (the pattern union, discriminated on `pattern_type`), `conditions` (a tuple, AND, no combinators), `repeatable` (default `False` — once-only), `consequences` (a tuple; empty is a normal shape — a narrative-only trigger is legal and useful), and `narrative` (`NarrativeBlock | None`). Two model validators do the heavy lifting at parse: `_conditions_never_consume` (`triggers.py:236-247` — "a trigger fires, it does not take") and `_consequences_carry_no_source` (`triggers.py:249-260` — the interpreter stamps `source` at fire time as `trigger:<id>`, `interpreter.py:476-482`). Both ride the batch's mandatory re-validation and the request parse, so the editor's builders simply never render the controls: `ConditionBuilder` takes `offerConsumes={false}` (the prop phase 15 built for exactly this, `condition-builder.tsx:2-5`), and no consequence form carries a source field — though `source` still serializes as `null` in every dumped command and must round-trip untouched.
2. **Trigger ids are unique in their own namespace and referenced by nothing in the document.** `validate_adventure` emits `trigger {id!r}: id is not unique` per duplicate (`adventure.py:602-603`); trigger and quest ids are separate namespaces with no cross-check. No document field references a trigger id — fired-marks live in saves (`session.fired_triggers`, `session.py:369`) and `source` stamps are runtime — so a `SetTrigger` rename cascades nowhere in the document: only the sidecar note key moves (`trigger:<old>` → `trigger:<new>` in `_remap_rules`, `documents.py:1105-1128`), and the delta pointer stays `/triggers` even on rename, unlike the monster and item renames whose cascades force whole-document deltas. The guide notes the one external consequence: renaming a trigger orphans its fired-mark in existing saves, osrlib's own posture (`MarkTriggerFired.trigger_id` is an open domain, `commands.py:1872-1878`).
3. **Order is semantics twice over, and `MoveTrigger` is greenfield.** The interpreter walks triggers in document order and fires each match inline before moving on, so a later trigger's conditions see what an earlier firing changed (`interpreter.py:294-318`); within a firing, consequences execute in authored order (`interpreter.py:355-362`). No editor surface ever sorts the list. No `Move*` op exists anywhere in `ops.py` — the only ordering prose is `AddLevel`'s insertion rule (`ops.py:603-615`), which *forbids* reorder because stored level order is rules-visible; triggers are the opposite case, where reorder is the point and the spec names the op. `MoveTrigger` is therefore designed here from scratch: `trigger_id` plus a destination `index` (0-based position in the reordered list), out-of-range rejected as `op_invariant` listing the valid range — the reject-don't-clamp posture `ResizeLevel` set. Consequence reorder needs no op at all: consequences live inside the spec, and the whole-value `SetTrigger` grain carries their order.
4. **The consequence union is closed by the type, not by a validator.** `ConsequenceCommand` (`commands.py:2214-2225`) admits exactly nine commands — `GrantItem`, `GrantCoins`, `AwardXP`, `SetFlag`, `SpawnMonsters`, `SpawnNpcParty`, `SetDoorState`, `PlaceParty`, `AdvanceTime` — with the exclusions reasoned in place (`commands.py:2192-2212`: the seven lifecycle commands are the interpreter's own vocabulary, `IdentifyItem` addresses a session-scoped instance, `RollDice` yields nothing authored content reads). A document naming any other command type fails to parse; the union *is* the enforcement. Per-command validators the forms must shape around: `SpawnMonsters` requires exactly one of `count_dice`/`count_fixed` with the dice string parsed (`commands.py:1681-1692`) — the encounter count control's exact gesture — and `PlaceParty.location` requires all four dungeon fields together or none (`dungeon.py:668-676`). The three character-addressed commands are `GrantItem`, `GrantCoins`, `AwardXP`; the only legal authored recipients are `"@party"` and `"@first"` (`adventure.py:379-386`). The selector constants live in osrlib (`triggers.py:61,69`), not the generated schema, so the frontend writes the literals itself.
5. **`SetDoorState` addresses a cell plus a side, never an edge key.** Its fields are `dungeon_id`, `level_number`, `x`, `y`, `direction` (`"north" | "east" | "south" | "west"`), plus four tri-state writes — `open`, `wedged`, `discovered`, `unlocked`, each `bool | None` with `None` meaning leave unchanged (`commands.py:1735-1763`; all-`None` is a legal no-op). The engine canonicalizes internally — `(2,0,south)` and `(2,1,north)` name the same door (`dungeon.py:120-139`) — and `validate_adventure` emits `names no door at (x, y) {direction}` when the addressed edge is not a door (`adventure.py:402`). The editor's door picker offers only actual door edges and emits the canonical form, making the no-door case unrepresentable by the control; a foreign document carrying one gets the new classification.
6. **Item domains split three ways across the trigger surface, and both pickers already exist.** `ItemAcquiredPattern.item_id` and `HasItemCondition.item_id` resolve against effective equipment ∪ shipped magic — `_dangling_condition_item`'s domain (`adventure.py:268-289`), which is exactly `GateItemPicker`'s (`item-picker.tsx:114`, whose header comment reserves it for this phase). `GrantItem.item_id` resolves against effective equipment *only* — no magic (`adventure.py:391`, the spec's "grants excluding magic items, matching the engine") — which is exactly the cache-domain `ItemPicker` (`item-picker.tsx:79`). `MonsterDefeatedPattern` and `SpawnMonsters` resolve against effective monsters — `effectiveMonsterCatalog` (`catalogs.ts:72`). No new picker is built.
7. **The interpreter's live behaviors shape the help text and justify the lints.** `MarkTriggerFired` issues *first*, before consequences, so a once-only trigger's mark burns even when every consequence drops (`interpreter.py:355-362`) — and the realistic drop is proven in osrlib's own suite: an `area_entered` trigger spawning into an area whose keyed encounter just opened loses the spawn to `session.command.encounter_in_progress` while the mark still burns (osrlib `tests/test_interpreter.py:412-424`, handler at `session.py:1259-1260`). That is the spawn-collision lint's whole justification. The cascade bound is `_MAX_MATCH_DEPTH = 4` (`interpreter.py:59`): generations 0–4 fire, deeper firings are suppressed unmarked with a `RecordNote`, and the moment is gone because clauses are edge-triggered (`interpreter.py:310,467-474`) — the cycle lint's justification. Flag comparison is strict-typed through `flag_values_equal` (a stored `True` never satisfies an authored `1`, `gates.py:167-194`) and `FlagSetPattern.value` of `None` matches any written value — so the typed value control phase 15 built carries over, joined by an any-value toggle. `TriggerFiredEvent` rides referee visibility (`events.py:836`): `fired` is table talk, `journal` is the player-facing voice — the narrative editor presents the pair honestly, per the spec.
8. **The machine phase 15 built already runs triggers.** `_rewrite_authored_layer` and the five `_cascade_*` helpers (`documents.py:1463-1650`) rewrite every trigger pattern, condition, and consequence site on every re-keying op — dungeon renames, level renumbers, area re-keys, monster and item renames — tested by `test_authored_cascade.py` against in-test trigger-bearing adventures. Phase 16 adds no cascade code; the authoring surface makes latent machinery live. Likewise in place: `NarrativeBlockEditor`'s `beats` prop with `Fired` and `Journal` already labeled (`narrative.ts:19-27`), `MiniLevelPicker` as the pick-a-cell-on-another-level control (`mini-level-picker.tsx:33-42`), the blocked-op triangle whose `translate_batch` assertion forces every new op to be blocked or translated (`overrides.py:157-174,177-203,427`), `addresses.py`'s top-level segment slot beside `monster:`/`item:`, `ForgeItemsBody`'s explanation-body pattern (`items-section.tsx:241-273`), and the section anatomy (`monsters-section.tsx`, `items-section.tsx`). Trigger error strings currently degrade to `validation_unclassified` verbatim, pinned by `test_diagnostics.py:172` — this phase inverts that pin.
9. **The validation strings are enumerable, and the owner discipline extends without strain.** Every trigger-owned line opens `trigger {id!r}: ` (`adventure.py:416-428`), with thirteen tail shapes total: five pattern shapes (unknown dungeon+level, unknown area, unknown dungeon, unknown item, unknown monster — `adventure.py:340-358`), one condition shape (unknown item, `adventure.py:362`), six consequence shapes (the selector violation, unknown item, unknown monster, unknown dungeon+level, no door, out of bounds — `adventure.py:383-413`, each sited `consequence {n}`), and the id-uniqueness line. Quest-owned lines share the same tails under `quest {id!r}` owners and never match a trigger classifier — they stay `validation_unclassified` until phase 17 grows their grammar. Enumeration confirmation renders each trigger id exactly as osrlib reprs it — the `_classify_bundled_item_collision` discipline (`diagnostics.py:246-260`).
10. **The advisory class is new severity-table rows, not a new tier.** `Finding.severity` is `Literal["error", "warning"]` and `Diagnostics` has exactly its three sources; the spec's advisory class is "warning severity by construction," so the three new checks are `SEVERITY` entries at `"warning"` (`lint.py:53-60`) appended after `area_overlap` in the vocabulary's order, each a whole-document sweep in `lint_adventure`'s grouped-by-check-id shape. The parity suite filters both implementations to `SHARED_CHECKS` (`test_lint_parity.py:26`), so editor-only codes cannot break parity — but its docstring names the exclusions and grows to name the advisory group. The measured perf pin (`test_lint.py:426`) re-proves the full pass stays trivially fast with three more sweeps.

## Work items

### 1. The trigger ops

Four new frozen ops in `ops.py`, adventure-scoped like the monster and item trios, embedding the osrlib model whole:

- **`AddTrigger`** — `trigger: TriggerSpec`. Appends to `Adventure.triggers`: authored order is firing order, and appending is the only insertion (a misplaced trigger moves after the fact).
- **`SetTrigger`** — `trigger_id: str`, `trigger: TriggerSpec`: whole-value replacement, first match among foreign duplicates. A differing `trigger.id` is a rename — no document site references a trigger id (research fact 2), so the rename cascades only into the sidecar: `_remap_rules` grows the `trigger:<old>` → `trigger:<new>` rule, riding the established remap-and-undo machinery. Delta pointer `/triggers` in every case, rename included.
- **`MoveTrigger`** — `trigger_id: str`, `index: int` (`ge=0`): splice out, insert at `index` in the resulting list. Out-of-range rejects as `op_invariant` naming the valid range; a same-position move applies as a harmless no-change batch, and the UI never posts one (the arrows disable at the ends). Pointer `/triggers`.
- **`RemoveTrigger`** — `trigger_id: str`, first match. Nothing references a trigger, so removal dangles nothing; the UI's two-step row confirm is the only guard.
- The invariant, `_require_trigger_id_free` beside its monster and item siblings, is strictly smaller than theirs: no shipped catalog exists to collide with, so it checks only the rest of `Adventure.triggers` (quest ids are a separate namespace and impose nothing). It runs on new or changed ids only — the carry-through rule: a foreign document's duplicate ids open, edit, and navigate, resolved first-match, flagged by the `trigger_id_not_unique` classification, never locked. An empty id needs no invariant: `TriggerSpec.id` carries `min_length=1`, so it rejects at request parse.
- Application: `_resolve_trigger` and `_apply_add/set/move/remove_trigger` helpers rebuilding `Adventure.model_copy(update={"triggers": ...})`, dispatched from `_apply_op`'s chain beside the item branches. The model validators arrive free: a consuming condition, a source-carrying consequence, a tenth command type, or a both-counts spawn all reject at request parse — the gated-slide precedent (`test_ops.py:346`), extended to the trigger shapes by test.

### 2. Forge blocking

- `_BLOCKED_MESSAGES` grows four entries, the ops sharing one message in the item wording's shape: "triggers have no override kind — the overrides vocabulary has no authored-layer surface." `_blocked_address` grows the matching branches: `trigger_address(op.trigger.id)` for `AddTrigger`, `trigger_address(op.trigger_id)` for the other three. No value-dependent branch is needed — triggers are whole-op blocked, and `translate_batch`'s closing assertion enforces that every new op took the blocked path.
- The frontend mirrors: `TRIGGER_BLOCKED_MESSAGE` in `lib/trigger-builders.ts` (the `monster-builders.ts` convention, mirrored verbatim from the server table); the Quests section's forge affordance (item 6); the map and level entry points routing to the blocked-op dialog client-side (item 7) — the server's 422 staying the authority for any batch that arrives.

### 3. Addresses and diagnostics

- `addresses.py` grows `trigger_address(trigger_id) -> "trigger:<id>"`, a top-level segment beside `monster:<id>` and `item:<id>`; the bare `triggers` scope joins `monsters` and `items` as the coarse degrade target.
- `diagnostics.py` grows a `_TRIGGER_SHAPES` table — the start-anchored owner prefix `trigger {id!r}: ` followed by thirteen tail shapes (research fact 9), classified under the enumeration-confirmation discipline: the owner id confirms by rendering each of the document's trigger ids exactly as osrlib reprs it; a confirmed id addresses `trigger:<id>`, a matching shape whose id confirms against no trigger degrades to the bare `triggers` scope, and anything else stays `validation_unclassified` verbatim. The codes, one per shape: `trigger_id_not_unique`; `trigger_pattern_unknown_level`, `trigger_pattern_unknown_area`, `trigger_pattern_unknown_dungeon`, `trigger_pattern_unknown_item`, `trigger_pattern_unknown_monster`; `trigger_condition_unknown_item`; `trigger_selector_violation`, `trigger_consequence_unknown_item`, `trigger_consequence_unknown_monster`, `trigger_consequence_unknown_level`, `trigger_consequence_no_door`, `trigger_consequence_out_of_bounds`. The dangling ids inside the tails are unconfirmable by definition and stay message text — only the owner confirms. Quest-owned lines never match (their owner prefix differs) and keep degrading verbatim until phase 17.
- `address.ts`: the `triggers` scope and `trigger:<id>` resolve to a NavTarget opening the Quests section — `trigger:<id>` with the trigger open, refusing (null) when no such trigger exists, the `monster:<id>` posture exactly. The diagnostics panel and map markers need no changes beyond the new addresses resolving; trigger findings are top-level addresses and draw no map marker.

### 4. The advisory lint class

Three new checks in `lint.py`, each a whole-document sweep appended after `area_overlap` in the vocabulary's order, each a `SEVERITY` entry at `"warning"` — advisory by construction, never escalating, never gating (research fact 10):

- **`flag_read_no_writer`** — a flag read over a key no `SetFlag` writes. Readers: every `FlagEqualsCondition` (door gates, transition gates, trigger conditions, and the clause conditions a foreign document's quests carry) and every `FlagSetPattern` (trigger `when` and foreign quest clauses). Writers: every `SetFlag` in trigger consequences *and* quest rewards — the writer set must include quests even before their authoring surface exists, or a foreign document lints falsely. The match is key-level and value-blind, by decision: the spec names the check over keys, a value mismatch is a different and rarer mistake, and strict-typed value matching across an open domain invites false positives. One finding per reading site, addressed to it — the door's edge address, the transition's cell address, `trigger:<id>` — except quest-owned readers, which carry `address=None` until phase 17 grows their grammar: visible and honest, never a navigable lie.
- **`trigger_cycle`** — `SetFlag` feeding `flag_set` back into a loop. The graph is triggers alone: an edge from A to B where A carries `SetFlag(key, value)` and B's `when` is `FlagSetPattern` over the same key with a value of `None` (any write) or one that satisfies `flag_values_equal`. Quests are not nodes by construction, not merely by scope: quest lifecycle beats fire once, so a path through a quest cannot loop. Detection is strongly-connected components; every SCC with a cycle (two or more members, or a self-loop) yields one finding naming its members in document order, addressed to the first member — deduped by member set, so a three-trigger loop is one row, not three. The message notes the engine's own behavior: the cascade truncates past its depth bound, dropping the rest as notes. A cycle of once-only triggers self-limits in play and is flagged anyway — circular flag wiring is almost always a mistake, and the check is advisory by construction.
- **`trigger_spawn_collision`** — a spawn aimed where a keyed encounter would already stand open: a trigger whose `when` is `AreaEnteredPattern` and whose consequences include `SpawnMonsters` or `SpawnNpcParty`, where the addressed area exists and carries a keyed encounter. Entering the area opens the keyed encounter, the spawn drops with `encounter_in_progress`, and a once-only trigger's mark still burns (research fact 7). Addressed `trigger:<id>`, message naming the area.
- The parity suite's docstring exclusion list grows the three ids; `SHARED_CHECKS` is untouched. The perf pin re-proves the full pass with the new sweeps. The reachability lint stays gate-blind and trigger-blind — nothing here touches the BFS.

### 5. Type aliases and typegen

- `frontend/src/types/index.ts` gains the phase 16 block in the phase 15 block's idiom: `TriggerSpec`, the seven pattern types, the nine command types, and `PartyLocation` re-exported; derived unions `TriggerPattern = TriggerSpec['when']` and `ConsequenceCommand = TriggerSpec['consequences'][number]` in the `ConditionSpec` convention; the four op types.

### 6. The Quests section

A new always-present nav entry, labeled "Quests" per the spec — the panel joins the nav in this phase with its trigger surface first, and phase 17 completes it. `NavTarget` grows a `quests` variant (`triggerId?`, `create?`); the section follows the items-section anatomy:

- **The trigger list** — document order, never sorted, order rendered as the semantics it is (the rows are numbered, and the header says triggers fire in this order). Each row: id in monospace, a module-notation pattern summary ("on entering area 3, level 1 of `stone-halls`"), condition and consequence counts, a repeatable badge, move up/down buttons posting `MoveTrigger` (disabled at the ends), and the two-step remove. Header action: "New trigger" — a create dialog collecting the id (prefilled next-free `trigger-<n>` over the trigger namespace) and the complete pattern through the pattern builder, committing `AddTrigger` with empty conditions, consequences, and narrative; everything else is detail-editor work. No fake references are ever seeded.
- **The pattern builder** — a kind select over all seven, per-kind fields committing complete values only (the `ConditionBuilder` discipline): `area_entered` — dungeon, level, and area selects over the document; `level_entered` — dungeon and level; `dungeon_entered` — dungeon; `town_entered` — no fields; `item_acquired` — `GateItemPicker` (effective items ∪ shipped magic, its reserved purpose); `monster_defeated` — the monster picker over the effective catalog; `flag_set` — a key input plus an any-value toggle, on by default (`value: None` matches any write); toggled off, the typed text/number/boolean value control, preserving type end to end.
- **Trigger conditions** — an add/remove/edit list of `ConditionBuilder` rows with `offerConsumes={false}`; the consumes control never renders because osrlib rejects a consuming trigger condition at parse.
- **The consequence builder** — a `ConsequenceBuilder` component plus an ordered list wrapper with per-row up/down (order is execution order; the list is form state committed whole through `SetTrigger`, so no op is involved). A command select over exactly the nine, then per-command forms: `grant_item` — the two-value selector, the cache-domain `ItemPicker` (effective equipment, no magic — research fact 6), quantity; `grant_coins` — the selector plus the five-denomination coins row (the cache coins precedent); `award_xp` — the selector plus amount; `set_flag` — key plus the typed value control (value required here); `spawn_monsters` — the monster picker, the dice-or-fixed count control (exactly one, the encounter-count gesture), distance in feet; `spawn_npc_party` — a basic/expert select, optional count dice, distance; `set_door_state` — the door picker (below) plus four three-way controls (leave unchanged / set / clear) for `open`, `wedged`, `discovered`, and `unlocked`; `place_party` — a town/dungeon kind select, the dungeon branch adding dungeon and level selects, a `MiniLevelPicker` cell pick, and a facing select; `advance_time` — a count and a round/turn/day unit select. The **selector** is a shared two-value `SelectorControl` ("Whole party" / "First living character") writing the literals — never a free id field, so a literal `character_id` is unauthorable; a foreign document carrying one surfaces as the `trigger_selector_violation` diagnostic. No form carries a `source` field, and committed commands round-trip the serialized `source: null` untouched.
- **The door picker** — dungeon and level selects plus a `MiniLevelPicker` variant that renders and offers only door edges; picking one fills the canonical `(x, y, direction)` (research fact 5). Seeding from a foreign value canonicalizes for display; only actual doors are offerable, so "names no door" is unrepresentable by the control.
- **The narrative editor** — `NarrativeBlockEditor` with `beats={['fired', 'journal']}` and the pair presented honestly: `fired` is the referee's line (`TriggerFiredEvent` rides referee visibility) and `journal` is the player-facing voice. The unread-beat warning and one-patch clear arrive with the component.
- **The detail editor** — pattern, conditions, consequences, the repeatable toggle (help naming the once-only default and that fired state lives in saves, not the document), the narrative editor, and `AuthorNotesCard` keyed `trigger:<id>`, remapped on rename. The id field carries the inline `op_invariant` rename prompt, the phase 4 gesture. All commits flow through `lib/trigger-builders.ts` update builders that compute from the committed document in the queue — the `itemTemplateKindUpdateOps` lesson from phase 15's review, load-bearing here because the consequence list edits sub-parts of a whole-value spec.
- **Quest presence, read-only** — a document carrying `Adventure.quests` (foreign or converted) renders one passive line naming the count and ids below the trigger list: the warn-and-name posture, no controls, the quest builder being phase 17's.
- **Forge mode** — the entry is present and navigates to the explanation body, the `ForgeItemsBody` pattern verbatim: the overrides vocabulary has no authored-layer surface, the gap is forge's recorded decision (osr-forge#39), detach offered in place. No list renders because no forge-assembled document can carry triggers.

### 7. Map and level placement

- **The area context menu** grows trigger entries in `stockingMenuEntries`: "Add trigger" always, minting a next-free-id trigger whose `when` is `area_entered` bound to that area, committing `AddTrigger`, and navigating to its detail in the Quests section — one gesture on the map, deep editing in the panel. The transition-dialog parallelism is the placement (the target comes from the grid), not the editing surface: a trigger's full builder is panel-weight, so no map dialog is invented for it. Below the add entry, one "Edit trigger '<id>'" per existing `area_entered` trigger targeting the area, navigating to it. In forge mode the add entry routes to the blocked-op dialog client-side.
- **The area glyph** — `drawTriggerGlyph`, a small pencil-weight lightning bolt joining the presence-glyph row beside the area key number (encounter, trap, treasure, and now trigger), drawn when any `area_entered` trigger targets the area — presence, not count, both themes via `MapTheme`. The renderer receives the set of trigger-bearing area ids for the current level, computed beside the existing marker plumbing; triggers are adventure-scope, so the set is derived, never stored. Like every glyph, it is documented in the guides — the editor has no in-app legend, per phase 15's amendment.
- **Level triggers hang on the level itself.** The level tab gains a small marker when any `level_entered` trigger targets its dungeon and number, and `LevelPropertiesDialog` gains a triggers block between the guidance field and the level features: this level's `level_entered` triggers listed by id (click navigates to the panel) and an "Add level trigger" action minting one bound to the level, exactly the area gesture at level scope. Forge mode routes the add to the blocked-op dialog.
- The placeless kinds — dungeon, town, item, monster, flag — author from the panel alone, by the spec's own sentence; no map surface is invented for them.
- Hit-testing, hover cards, and `markersFor` are untouched: the glyph is paint, navigation lives in the context menu and the panel, and trigger findings carry top-level addresses that draw no marker.

### 8. Fixtures and tests
