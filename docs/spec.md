# osr-editor specification

A local GUI application for creating and modifying adventure modules playable by [osrlib](https://github.com/mmacy/osrlib-python)-powered games. osr-editor authors the same stamped `adventure.json` documents that [osr-forge](https://github.com/mmacy/osr-forge) produces and [osr-web](https://github.com/mmacy/osr-web) plays, and it is the graphical review-and-correction tool the forge spec anticipated its consumers would build. It runs as a local web app: a FastAPI backend that imports osrlib and osr-forge, serving a React frontend to the browser.

## Vision

One tool for the whole module lifecycle: convert a PDF module with osr-forge, review and correct the draft on a graph-paper map beside the scanned pages, or author an adventure from a blank grid — then validate it and publish it to osr-web. The editor never reimplements rules or invents formats; osrlib's pydantic models are the schema, osrlib's validators are the referee, and osr-forge's artifacts are the conversion contract. The editor's job is to make those contracts directly manipulable.

Two principles govern everything:

**The backend is authoritative.** The FastAPI process holds the working document as real osrlib model objects. The frontend sends edit operations and renders what comes back — updated state plus live diagnostics. TypeScript types are generated from the pydantic models' JSON Schema, so the frontend is typed against the same source of truth it never re-implements.

**Forge output stays reproducible.** A module converted by osr-forge is corrected through `overrides.yaml`, never by hand-editing generated output — the editor is an overrides-authoring surface over forge's pure `assemble`/`check` loop. Direct editing is for native projects; crossing from one world to the other is an explicit, recorded act.

## Non-goals

- **No hosting, multi-user, or auth.** Single-user, localhost-only, one process. Publishing to PyPI (a later phase) ships the same local tool, not a service. The design still keeps the door open rather than building into a corner: every route resolves its caller through a single auth dependency that today returns the local user, and persistence sits behind the `ProjectStore` protocol — the two seams a hosted future would swap (see future extensions).
- **No rules implementation.** Validation, generation, and play all call osrlib — including the SRD stocking procedure, which osrlib grew when the editor became its first consumer; the editor owns only stocking seeds, target selection, and op assembly (see authoring aids). The adventure planner holds the same line: its baselines are sampled from osrlib's own procedures under a recorded seed, never restated as editor constants — the two owned defaults that section pins excepted (see the adventure planner).
- **No party or pregen authoring.** `adventure.json` has no party surface and osr-web imports parties only from saves. Future work, contingent on the ecosystem growing a pregen surface (already an open question in the forge spec). The adventure planner's party model is not an exception: `PlanSpec` is editor metadata in the sidecar, and no party surface enters the document (see the adventure planner).
- **No save editing.** Saves are session runtime owned by osrlib and the games.
- **No SRD catalog editing.** Shipped osrlib data is immutable; bespoke monsters are adventure-bundled `MonsterTemplate`s, exactly as osrlib 1.2 defines them, and bespoke items are adventure-bundled `ItemTemplate`s, exactly as osrlib 1.5 defines them (see the authored layer).
- **No art assets.** The adventure model carries prose, not images; the editor renders maps from geometry. Forge-workdir page images appear in review UI but are never part of the deliverable.
- **No pixel-perfect map import.** Inherited from forge: geometry comes from the connection graph and human correction, not automated cartography matching.

## The two project types

A project is a directory on disk. The editor recognizes two shapes and adapts the whole UI to which one is open:

**Native project** — a directory containing a stamped `adventure.json` (the deliverable) and `editor.json` (editor-only sidecar: view state, per-entity author notes, stocking seeds, provenance, content-library drop records and the displaced-content stash, and the adopted plan; its own additive-only `schema_version`). Created from scratch in the editor, or by detaching from a forge workdir. Edits mutate the document directly (through the document service). Conventional name `<name>.osr/`, but any directory matching the shape opens.

**Forge-backed project** — an osr-forge workdir (`<name>.forge/`), detected by the presence of `run.json` — forge's own definition of a workdir, and the only marker an estimated-but-unconfirmed one carries (it has rendered pages and no stage caches at all). The editor never writes `adventure.json` here; every edit becomes an `overrides.yaml` entry and the editor re-runs `osrforge.assemble()` — pure, deterministic, and fast by forge's contract — so the draft, `report.json`, and previews always reflect the current corrections. The review UI shows report flags, per-area confidence, the workdir's rendered PDF pages, and SVG previews beside the live map. The editor keeps its `editor.json` sidecar in the workdir root too — an editor file, not a forge artifact; forge reads only its own files. A workdir whose conversion never completed opens into the pipeline view (per-stage status, resume, rerun) rather than review, since review requires an assemblable workdir.

**Detach** converts a forge-backed project to a native one: the current assembled `Adventure` is written as a new native project, with provenance (source workdir path, forge and osrlib versions, date) recorded in `editor.json`. Detaching is for edits `overrides.yaml` cannot express — adding a whole dungeon or level, changing a `WanderingSpec`, bundling a monster the module never mentions — and the editor offers it in place when such an edit is attempted, warning that the forge re-run loop is severed. Map correction is deliberately *not* on that list: geometry is one of forge's override kinds, so redrawing a level's rooms, walls, and doors stays inside the reproducible loop (see forge-backed editing).

## Documents and versioning

- The deliverable is `stamp_document("adventure", Adventure.model_dump(mode="json"))` — the same de facto document kind forge writes and osr-web checks with `check_document(document, "adventure")`. osrlib owns the envelope (`kind`, `schema_version`, `engine_version`, `payload`).
- On open, an older `schema_version` is accepted (osrlib's rule) and the document is re-stamped at current versions on next write; a newer one fails fast with osrlib's own error, surfaced with the remedy (upgrade osrlib).
- Additive osrlib growth *within* a schema version is guarded too: on open, the editor re-serializes the parsed payload and takes a one-way structural diff against the source — keys present in the source but absent from the re-serialization. Any such field triggers a prominent warning before the first write — an always-saved editor would otherwise silently drop fields a newer osrlib authored — with the upgrade remedy named. The reverse direction (defaults the pinned models add to an older document) is normal normalization, not loss, and warns nothing.
- Native-project serialization is canonical — pydantic field order, 2-space indent, `ensure_ascii=False`, trailing newline — so a no-op session over a document the editor wrote produces no diff and projects live happily in git. A document stamped by an older engine normalizes on its first write (the re-stamp rule plus any additive model defaults), one honest diff rather than byte identity that cannot hold.
- The editor is **always-saved**: a committed operation persists immediately (native: rewrite `adventure.json`; forge-backed: rewrite `overrides.yaml` and re-assemble). There is no dirty state and no save button; undo/redo is the safety net in-session, and git is the safety net across sessions (project directories are plain, diff-friendly files by design).

## Architecture

```text
osr-editor/
├── src/osreditor/          # Python package: FastAPI app + document service
│   ├── app.py              # routes, per-project locks, static serving
│   ├── projects.py         # project detection, open/create, recents
│   ├── store.py            # ProjectStore protocol + local filesystem store
│   ├── documents.py        # working-document store, ops, undo/redo, revisions
│   ├── ops.py              # edit-operation vocabulary (typed pydantic models)
│   ├── lint.py             # live structural lint (forge finding vocabulary)
│   ├── overrides.py        # op → overrides.yaml translation for forge-backed mode
│   ├── forge.py            # osr-forge bridge: assemble, check, rerun, convert, estimate
│   ├── aids.py             # stocking, treasure/encounter preview, prose assist
│   ├── planner.py          # adventure planner: plan derivation, sampled baselines, budget audit
│   ├── publish.py          # export + publish-to-osr-web
│   └── static/             # built frontend (generated at build time, shipped in wheel)
├── frontend/               # React + TypeScript + Vite source
│   └── src/types/generated/  # TS types generated from pydantic JSON Schema
├── scripts/                # type generation, dev orchestration
├── tests/                  # pytest; tests/e2e/ Playwright
└── docs/                   # this spec; mkdocs site later
```

- **Backend:** FastAPI + uvicorn, importing `osrlib` and `osrforge` directly. One in-memory working document per open project, guarded by a per-project lock (osr-web's proven pattern). Long-running work (conversion) runs on a worker thread with cooperative cancellation — a cancel raises out of the `on_progress` callback at the next stage boundary, so completed stages persist and no artifact write is ever interrupted mid-file; everything else is synchronous request/response.
- **Storage:** every project artifact read and write goes through a `ProjectStore` protocol (list, read, write artifacts by project) — forge's `ModelProvider` seam, applied to persistence. The local filesystem store ships; blob or database stores are later drop-ins. Forge operations always run against a locally materialized workdir (osr-forge is file-based), so a remote store syncs workdirs down and back rather than teaching forge about remotes — the same archive-the-workdir pattern osr-web's planned conversion worker uses.
- **Frontend:** React + TypeScript + Vite, with UI chrome built from shadcn/ui components (vendored Radix primitives, styled with Tailwind CSS) — pre-built parts for the panels, forms, dialogs, and trees that make up most of the editor, themed rather than hand-built. The map pane is the one fully bespoke surface: a 2D `<canvas>`. State management is chosen at phase-plan time (a small store like zustand; not spec-relevant).
- **Type generation:** a `uv run` script emits JSON Schema from the osrlib models and the editor's own API models, and generates TypeScript declarations into `frontend/src/types/generated/`. CI regenerates and fails on diff — the same drift discipline as osrlib's SRD pipeline.
- **Transport:** REST over `fetch`, polling for long-running progress (conversion) — the osr-web precedent; no WebSockets.
- **Dev loop:** Vite dev server proxies `/api` to the backend; production and the wheel serve the built `static/` directly, so runtime needs Python only. Node is a development-time dependency exclusively.

## The document service

The heart of the backend, and the editor's echo of osrlib's own commands-in/events-out philosophy: **operations in, state and diagnostics out.**

- An **edit operation** is a typed pydantic model naming a domain action, not a JSON patch: `SetAdventureField`, `SetTownField`, `AddDungeon`, `AddLevel`, `ResizeLevel`, `SetEntrance`, `SetEdges` (a batch of canonical edge-key → `Edge | None` assignments), `CreateArea`, `SetAreaCells`, `SetAreaField`, `RemoveArea`, `SetEncounter`, `AddFeature`, `SetFeatureField`, `RemoveFeature`, `SetTrap`, `SetTreasure`, `SetWandering`, `AddTransition`, `RemoveTransition`, `AddMonsterTemplate`, `SetMonsterTemplate`, `RemoveMonsterTemplate`, `AddItemTemplate`, `SetItemTemplate`, `RemoveItemTemplate`, `AddTrigger`, `SetTrigger`, `MoveTrigger`, `RemoveTrigger`, `AddQuest`, `SetQuest`, `MoveQuest`, `RemoveQuest`, `SetLevelField`, and kin. The vocabulary grows additively.
- Operations post in **batches** that apply atomically and form one undo step, so a compound gesture (draw a rectangle room = create area + open interior edges) is a single unit of work and a single Ctrl+Z.
- Because osrlib content models are frozen, applying an op rebuilds the affected subtree and produces a new `Adventure` value. Undo/redo is a bounded in-memory stack of document values (documents are small — the largest known is ~300 KB); nothing clever, nothing persisted.
- Every batch returns the new **revision id**, the changed subtree, and refreshed **diagnostics**. Requests carry the revision they were computed against; a stale revision is rejected with 409, which makes a second browser tab safe rather than silently destructive.
- A batch that would produce an invalid model (a pydantic validator fails) is rejected whole with the validator's message mapped to the offending field — the document in memory is never invalid at the model level. Cross-reference problems (a dangling `template_id`, an out-of-bounds transition target) are *legal to have* while editing and surface as diagnostics instead; `validate_adventure` cleanliness is the publish gate, not an editing precondition.
- `ResizeLevel` shrinking below existing content is rejected listing every offender (areas, features, transitions, entrance) rather than auto-mutating them.

### Diagnostics

Three tiers, recomputed live after every batch and rendered in a persistent diagnostics panel with click-to-navigate:

1. **Model validity** — enforced by construction (see above); the panel never shows these because they can't be committed.
2. **Content validation** — `validate_adventure(adventure, load_monsters(), load_equipment())`, every error listed with location.
3. **Structural lint** — an editor-owned, incremental implementation of the static graph checks, using forge's finding vocabulary where the checks coincide (`edge_invalid`, `area_unreachable`, `orphan_cell`, `secret_only_access`, `transition_unpaired`) plus editor-only findings (`area_overlap` — overlapping area cells are legal but almost always a mistake) and the authored layer's advisory class — data-flow checks over flags, triggers, and rewards, warning severity by construction (see the authored layer). The editor owns this engine because live-per-edit lint needs to be in-process and incremental; forge's batch `check()` (including its smoke delve) additionally runs for forge-backed projects and its findings merge into the same panel.

## The map editor

The primary surface: a top-down grid per level, rendered as literal graph paper. osrlib's spatial model shapes the tools — all cells of a `width × height` level exist; an edge absent from the map is a wall; only `open` passages and doors are authored, always under the canonical north/west edge key.

Tools:

- **Room** — drag a rectangle: creates an `AreaSpec` over those cells and opens interior edges, one undo step. The area is immediately keyed (next free id) and selected for content editing.
- **Corridor** — drag a path: opens the edges along it. Corridor cells are simply cells in no area, per osrlib's convention.
- **Wall/door** — click an edge to cycle wall → open → door; a door inspector sets `normal`/`secret`, `stuck`, `locked`, `starts_open`, and the door's gate (see the authored layer). Drag to paint edges in a line.
- **Area** — lasso or paint cells into an existing or new area; areas render as tinted regions with their key numbers, like a printed module map.
- **Entrance** — place the level's entrance cell (validation requires at least one per dungeon).
- **Transition** — click the source cell, pick kind (stairs up/down, trapdoor, chute), then pick the target dungeon/level/cell and facing on a target-level picker. Stairs offer auto-reciprocal creation; trapdoors and chutes are one-way by rule. A transition carries a gate the way a door does (see the authored layer).
- **Import geometry** — bring a level's grid in from outside: copy from another project's level, or read an external map format through a geometry importer (below). Either way the map editor doubles as a standalone map designer — draw a level in a scratch project, then swap it into the real module. In a forge-backed project the import lands as a `geometry:` override, so even a wholesale replacement map stays inside the reproducible correction loop. Replacing a level that holds content offers to move that content to the content library first (see content editing), so a map swap never means starting the stocking over.
- **Select/inspect** — click anything to open its editor panel; hover shows the cell/edge ref, and resting on an area raises its hover card (see content editing).

Level management: tabs per level within a dungeon, dungeon switcher above; add/remove/resize levels and dungeons with the invariants (unique ids, unique level numbers, min one of each) enforced by the ops. Map glyphs follow classic module-map conventions — door ticks on walls, "S" in the gap for secret doors, stair treads, arrows for one-way drops — so the on-screen map reads like the maps these modules were printed with.

### Geometry importers

Import is a seam, not a feature list. A `GeometryImporter` is a small protocol — a `format_id`, a label, `sniff(path)`, and an import call returning an editor-defined `ImportedGeometry` payload: one or more levels of cells, edges, and doors, plus whatever else the source knows — keyed areas with names and descriptions, an entrance, transitions, module title and description offered for adoption. Importers register through a Python entry-point group (`osreditor.importers`), so a converter for any map format is an installable package that never touches editor code; the built-in import-from-project tool is itself the first implementation, which keeps the protocol honest. Imported geometry lands as ordinary op batches — undoable, immediately linted, a starter map rather than a locked artifact — and each importer owns its format's judgment calls (grid scale onto 10' cells, coordinate normalization, door-type mapping), flagging what it guessed.

The motivating external target is Watabou's One Page Dungeon JSON export, whose shape — room rectangles, doors with position/direction/type, keyed positioned notes, a title and story — maps closely onto cells, door edges, keyed areas, and adventure metadata. The one real impedance is that an OPD door is a floor *cell* while an osrlib door is an *edge* between cells; the source's own geometry resolves it — the door cell stays floor, and the door lands on the edge between the door cell and its direction-vector neighbour. That converter is phase 8; the seam ships first, in phase 2.

## Content editing

Stocking is map-first — the map is the picker, and no workflow ever starts from a long id list:

- **Click an area to open it; right-click for the stocking menu.** The context menu offers exactly what the area can hold — add or edit the encounter, features, trap, treasure, or description, or roll SRD stocking for the room (see authoring aids) — with entries reflecting current state: an area that already has an encounter shows edit and remove, not add.
- **The area panel reads like a printed keyed entry**, not a form of forms: description prose up top, then one compact card per content kind — encounter, treasure, trap, features — each summarizing itself in module notation ("3d4 orcs", "treasure type C", "poison needle: save vs. poison or 1d4"). Empty kinds are single-click adds, cards expand in place to edit, and removal is the card's own action; the deep forms (the trap builder, the monster editor) appear only inside an expanded card.
- **The map shows stocking state at a glance.** Area key numbers render hollow for empty rooms and filled for stocked ones, with small glyphs for encounter, trap, and treasure presence; hovering an area shows its one-line contents, and resting there under the select tool raises a hover card beside the area — id and name, the description, and one module-notation line per carried kind — that drops the moment the pointer leaves. The card is read-only and pointer-transparent, and it yields the hover to every surface that owns it first: an in-flight gesture, an armed library entry, and an entry drag all suppress it. Next/previous-area keys walk rooms in key order, and a filter dims everything but unstocked rooms — stocking a big dungeon is a walk through it, not a spreadsheet session.
- **Pickers are type-ahead, never scroll-lists.** The monster picker searches the effective catalog as you type, surfaces this adventure's bundled and recently used monsters first, and takes the count inline; the equipment picker works the same way.

The drag-from-palette toolbox this model deliberately left room for is the content library (below): finished modules — and shared content packs — as the palette, layered on without changing the model.

The field-level contracts behind the cards:

- **Prose** — name and description, in a serif editor sized for reading aloud. Per-area author notes live in the sidecar, never the deliverable.
- **Encounter** — monsters as `template_id` + count (dice or fixed, exactly one, per the model), with a searchable picker over the effective catalog (shipped SRD plus this adventure's bundled templates); pinned alignment (constrained to the template's options), `aware`, and pinned `stance`.
- **Features** — treasure caches, construction tricks, and custom features, bound to the whole area or a specific cell. The contents — item ids picked from the effective catalog (shipped equipment plus this adventure's bundled items — see the authored layer), coins and named valuables on forms mirroring `Coins` and `ValuableSpec` — are offered on treasure caches only, because osrlib's take and inspect handlers reject any feature of another kind, so contents elsewhere are unreachable in play. Leaving the cache kind clears the contents with the trap in the kind change's own batch — one undo step, and undo is the way back. A non-cache feature that *arrives* carrying contents keeps them (an incoming document is never silently rewritten) and warns, naming them, since the gate would otherwise hide contents that still serialize and still publish; the kind select is the recovery.
- **Traps** — a builder over `TrapSpec`/`TrapEffect`: room traps on areas, treasure traps on caches (the split is enforced by the models), affects, and the composable effect fields — damage, volley, save, condition + duration, fall, slide transition, and the `manual` prose fallback for what B/X leaves to the referee. The trigger follows the kind's domain: a room trap's is authorable — osrlib springs `enter` when the party steps onto a cell of the area and `open` when a door of the area swings, either side, so the builder offers the choice with each value's springing action named — while a treasure trap shows no trigger at all: the cache-open path springs it unconditionally, and the model rejects a treasure trap carrying `enter` at parse.
- **Treasure** — `AreaTreasureSpec`: treasure-type letters or the unguarded roll, exactly one.

Level scope: `WanderingSpec` (chance-in-six, interval, and the optional inline `EncounterTable` override on a d20 row form with osrlib's cover-1-to-20 rule enforced live), and the ambient `guidance` slot — per-level narrator steering, the same audience as a narrative block's guidance field (see the authored layer). Adventure scope: name, description, hooks, and the town (name, description, services, per-dungeon travel turns).

### The content library

The third stocking mode, alongside hand-keying and SRD stocking: stock a map by dragging finished rooms onto it. Two workflows motivate it, both first-class. Build a native project around an imported One Page Dungeon map and stock it from a converted module — the module as palette, the OPD map as canvas. Or swap an OPD map into a level of an existing project and re-place that level's own displaced content by hand. Neither auto-populates anything; curated placement, room by room, is the point.

**Everything the library opens is a content pack.** A pack is a set of entries — geometry-free room projections, each carrying a stable entry id and any subset of name, description, encounter, trap, treasure, and features — plus the bundled monster templates those entries reference and optional wandering tables. The pack is an osrlib-owned document kind: osrlib grows `content_pack` as an additive release with the editor as its first consumer — the SRD-stocking precedent — owning the entry and `ContentPack` models, a `validate_content_pack` beside `validate_adventure`, and, decisively, payload evolution. A pack persists osrlib model dumps, and shared packs are the family's longest-lived artifacts, so their acceptance rules must be osrlib's own: the accepted-older, re-stamp-on-write posture adventure documents ride, normalization through model validation included. Today's `MIGRATIONS` chain serves saves alone — if a payload-breaking change ever ships, growing it kind-aware is that osrlib release's work, landing beside the models it reshapes and never re-derived outside them; phase 11's osrlib release carries only the models, the validator, and the kind. The editor owns every surface a user touches. The entry is also where unplaced content legitimately lives: an `AreaSpec` requires cells by design, and the pack keeps that invariant out of the document by holding placeless rooms itself. Packs have three habitats, and the panel, drops, closure, and provenance never care which one a pack came from:

- **Derived** — opening a project projects its document into pack shape in memory. The currently open project projects its working document directly — no disk read, revision-consistent; another native project loads and validates through the `ProjectStore` seam; a forge workdir assembles through the forge bridge — current-first, the same rebuild-on-open posture project open pins, the writes being forge's own artifacts — and an unassemblable workdir refuses with the same incomplete-conversion remedy as review. The editor writes nothing to a source, ever — no overrides, no sidecar — and a source open is a read, not a second project session. Entry ids are the source areas' addresses; pack identity is the source project's path. The panel's open-source list is remembered per project in the sidecar's view state — the same species as the active level and the cameras — and restored on return, each restoration an ordinary fresh open, never a sync; an identity that no longer opens surfaces its refusal once and is forgotten. The `GeometryImporter` payload stays a map — geometry and identity prose, never keyed content; the library is its content-bearing counterpart, not an extension of it.
- **Embedded** — each stash act stores one stamped pack in the sidecar (below), vetted on open under the same accepted-older rule as any stamped document.
- **Standalone** — a pack saved as a stamped file, loaded and shared: phase 12's surface, designed here so the model is identical from birth.

The interaction contracts:

- **Entries preview in place.** Each row discloses what it carries before any placement — the description plus one module-notation line per carried kind, monster names resolved through the shipped catalog and the pack's own bundled templates — and a panel-level toggle expands or collapses every open pack's rows at once. The preview is panel state and read-only by the panel's own rule: it opens and closes; every write stays a drop.
- **A drop writes exactly the kinds its entry carries**, assembled client-side like an import and posted as one ordinary op batch — `SetAreaField` + `SetEncounter` + `SetTrap` + `SetTreasure` + `AddFeature` for the carried kinds only: one undo step, immediately linted, and — template closure aside (below) — translatable to overrides, so a forge-backed target stays inside the correction loop. Merge is the default posture, not a mode: a trap-only entry dropped on a room full of monsters and treasure touches nothing but the trap slot. Features are the one plural kind and always append, re-minting ids under the level's next-free convention. The single-slot kinds prompt on collision — one dialog naming the colliding kinds with per-kind replace-or-keep choices, replace preselected, the choice remembered while that pack stays open in the panel (panel state, never persisted) — so stocking an OPD level whose every area arrives carrying Watabou's note text prompts once, not thirty times. A click-to-place fallback (select an entry, click an area) serves keyboards, trackpads, and assistive tech. Drop targets are existing areas only — corridors are unkeyed floor, and creating areas stays the area tool's job.
- **Geometry never copies.** Cells, edges, doors, and transitions stay behind — transitions live on levels, not areas, and the target map is the one being kept. A slide trap's embedded transition may arrive dangling; that is the standard diagnostics posture, legal while editing and gated at publish.
- **Monster templates travel by closure.** A dropped encounter or wandering table that references a pack-carried template brings it along as `AddMonsterTemplate` in the same batch: an identical id and definition already in the target is reused (thirty rooms from one module mint zero duplicates), a differing one re-mints `<id>-<n>` — the monster-clone convention — and the dropped reference is rewritten. In a forge-backed target a closure-bearing drop blocks whole in place with the detach offer — `AddMonsterTemplate` has no override kind, and bundling a monster the module never mentions is already a named detach case; drops that resolve entirely against the shipped catalog or templates the target already carries translate clean. Packs are self-contained by rule: saving one computes the closure of every non-SRD template its entries reference, and a loaded pack that dangles anyway surfaces diagnostics in the panel and still drops. Same-project and stash drops need no closure; their references already resolve.
- **Wandering tables copy at level scope.** Per-room drops never touch the wandering table, so a pack's level rows offer copying theirs — a `SetWandering` batch with the same template closure. In a forge-backed target it blocks in place with the detach offer, like any op without an override kind.
- **Provenance is a copy record, never a link.** Every copy — a room drop, a wandering-table copy, a phase-12 template adoption — records target address (area, level, or monster) → pack identity and pack-side id in the sidecar, powering used/unused badges on the palette; stocking is a checklist activity and rarely one sitting. Pack identity is pinned per habitat: a derived pack is its source project path, a stash pack carries a minted id, a standalone pack carries a stable id minted into its metadata at save — so a moved pack file keeps its badges, while a moved source project degrades to the badges already earned: the copies are complete, and nothing ever re-syncs. Copy records are a third addressed map in the sidecar, joining the existing rename-remap lockstep with notes and stocking streams, undo replay included. Re-dropping is allowed; used means at least once.
- **Displaced content feeds the library.** The two bulk content-destroying acts — a replace-mode geometry import and clear level content — offer to move the level's rooms and wandering table into the stash before the batch applies; declining proceeds with the plain destructive batch, undo the only way back. Each stash act mints one stash pack — labeled by its dungeon, level, and date, entry ids frozen as the areas' addresses at capture — and the panel lists every stash pack the sidecar holds. This is the swap-in workflow: replace a level's map with an OPD import, keep its content in the library, re-place it room by room. A stash pack reads fully used when every entry, and its wandering table if one was captured, has at least one copy record. Deletion is manual, behind a destructive-action confirm naming what is discarded, and stays on the sidecar's unguarded channel by the same owner sanction — the 409 discipline protects the deliverable, the stash is a recovery buffer, and git remains the cross-session net. Undoing the replace restores the level while the stash pack persists — a harmless duplicate, not a conflict, and deletable. The stash is the one sidecar field that carries content rather than metadata, an owner-sanctioned posture change within the additive-only schema.

**Standalone packs (phase 12)** are the sharing surface — the DLC model: a friend's bespoke monsters, traps, and treasures stocking your dungeon. A pack file is `stamp_document("content_pack", …)`, vetted on load with `check_document` — the ordinary family envelope, riding osrlib's schema counter: an older version is accepted on load and re-stamped by the next save that writes the file, the adventure document's own rule. Save the stash or any selection of entries as a pack (closure computed; metadata — name, description, author — prompted; a stable pack id and per-entry ids minted into the file, so badges follow the pack wherever the file travels); open a pack file in the panel like any other source; a monsters-only pack lists its templates for one-click `AddMonsterTemplate` under the same reuse-or-re-mint rule. Saving a pack is the same explicit user-invoked export the licensing fence already allows: a pack cut from a converted module is the user's to have, and what they share is their responsibility — exactly as it is when publishing the conversion itself.

## The monster editor

Full stat-block authoring over `MonsterTemplate`, in scope for 1.0 as a first-class surface:

- **Create from scratch** or **clone-and-modify** any catalog monster (the fastest route to "like an orc, but…").
- The form covers the whole model: AC pair (with the attack-roll-required coupling the validator enforces), hit dice (count/die/modifier/asterisks or fixed hp), THAC0 and attack bonus, attack routines built as ordered lists of attacks (count, name, damage dice or fixed, by-weapon, effect tags), movement modes, the five saves plus save-as, morale with alternates, alignment options, XP with role notes, number appearing (dungeon/lair), treasure refs, abilities (tag, name, prose, `manual` flag, params), defenses (harmed-only-by, reductions, energy defenses, condition immunities), and categories. Editor-authored templates set `page` to the empty string, forge's own convention for unpaged blocks.
- Bundled templates live on `Adventure.monsters`; the id-collision rule (never shadow the shipped catalog) is enforced as an op-level rejection with a rename prompt — the models can't see the shipped catalog, and a collision is never intentional, so the editor refuses it at commit instead of letting it linger as a diagnostic. `validate_adventure` remains the authoritative gate.
- In forge-backed projects the correction surface is a *printed-notation* form whose fields are exactly forge's `StatBlockOverride` (AC as printed — "5 [14]" — hit dice as "3+1", attack lines as written), because `monster_templates:` patches land pre-mapping by forge's contract and reviewing against the printed page is the point. The report's `derived` list badges the mapped fields; a derived field with no raw counterpart (treasure, notably) is corrected by a `monsters:` remap, an encounter replacement, or detach — never by hand-editing mapped output.

## The authored layer

osrlib 1.5 grew the playable story surface — bundled items on `Adventure.items`, gates on doors and transitions, data-authored triggers run by a library `Interpreter` the host registers, quests with lifecycle beats and rewards, the three-audience narrative block, `SessionMode.VICTORY` — and 1.6 finished it with objective display names during osr-web's adoption, which proved the whole model plays end to end. The editor is its authoring surface, on the standing growth path: osrlib owns the schema, the generated types pick it up the moment the pinned floor reaches the models, the op vocabulary grows additively, and each as-built constraint is enforced the way the editor always enforces schema truths — unrepresentable by construction where a control can be shaped, a diagnostic where a foreign document can arrive already carrying the problem.

**Bundled items.** `Adventure.items` bundles the same four template kinds the shipped catalog is made of — weapon, armour, gear, ammunition; never magic items — and the item editor mirrors the monster editor: create from scratch or clone-and-modify a catalog item, full forms over each kind's model, its own nav section beside Monsters. The collision rule is stricter than the monster rule's never-shadow: a bundled id may collide with neither the equipment catalog, the magic-item catalog, nor the rest of the bundle — one item id names one thing per session; `has_item` stands on that — and the editor refuses a collision at commit with a rename prompt, the monster-template posture exactly; `validate_adventure` remains the authoritative gate. Every item picker searches its site's true domain: treasure-cache contents and grant consequences resolve against the effective catalog (shipped equipment plus this adventure's bundle, grants excluding magic items, matching the engine), gate conditions and acquisition patterns against the effective catalog plus shipped magic. The town shop is a deliberate carve-out — a bundled id is never purchasable (`items.purchase.not_stocked`), the shop must not sell a second copy of the quest idol — so no editor surface ever suggests stocking one.

**Gates.** A gate is `requires` on exactly two carriers — a door and a level-placed transition; it hangs nowhere else, and a trap-effect slide is a forced relocation, not an attempt, so the trap builder's transition sub-form has no gate control (osrlib rejects one at parse; the editor makes it unrepresentable). The gate card on the door inspector and the transition dialog holds one condition — `has_item`, `flag_equals`, or `effect_active` — plus the narrative block. `consumes` (the toll) is a `has_item` field — the other condition kinds have nothing to take — and is offered on gate conditions alone: a trigger or quest clause that consumes rejects at parse, so the clause builders never show the control. A locked-and-gated door requires both — the gate composes with the existing door flags rather than replacing them — and gated doors and transitions badge on the map in the glyph language. Reachability lint stays gate-blind by decision: `area_unreachable` treats a gated door like a stuck or locked one — satisfiable in play — and the unsatisfiable case belongs to the advisory key-not-placed lint, not the BFS.

**Triggers.** Authored wiring on `Adventure.triggers`, located by pattern rather than placed on a cell: seven patterns — area, level, dungeon, and town entry; item acquired; monster defeated; flag set. Area triggers place from the map the way transitions do — the target picked on the grid, a glyph rendered at the pattern's address, add-a-trigger on the area's context menu — level triggers hang on the level itself (its tab, not a cell), and the placeless kinds — dungeon, town, item, monster, flag — author from the panel. A trigger carries conditions (consume-free by construction), a `repeatable` toggle against the once-only default, and consequences drawn from exactly the closed nine-command union — the grant, flag, spawn, door, place, and time family; no lifecycle commands, no `IdentifyItem`, no `RollDice` — so the builder offers that union and nothing wider, with `SetDoorState` picking its door on the map. The three character-addressed commands take their recipient from a two-value selector control — `@party` or `@first` — never a free id field: a literal `character_id` cannot exist in a valid document, so the editor makes it unrepresentable rather than merely lint it; `source` is the issuing trigger's stamp and never surfaces. Document order is semantics — triggers fire in authored order, quests seed in it — so the authored-layer lists preserve order, expose reordering as ops (`MoveTrigger`, `MoveQuest`), and never sort.

**Quests.** The quests panel joins the nav. A quest is activation as a `TriggerClause` — a trigger pattern plus gate-vocabulary conditions, run by the same matcher triggers use, so the two surfaces cannot drift — or no activation for a standing charge; at least one objective, each with a completion clause, a display name that falls back to its id when unauthored, and hidden/reveal, the reveal clause offered only on a hidden objective since osrlib rejects it elsewhere; rewards from the same consequence union under the same selector rule; `all`/`any` completion; and `concludes_adventure` — the one authored field behind `SessionMode.VICTORY`. Quest lifecycle beats journal their display text as themselves, so the quest and objective narrative editors carry no separate journal voice.

**Narrative blocks.** One model, three audiences: display beats a renderer shows verbatim, the journal form, and LLM guidance never shown verbatim, plus speaker attribution. The block editor offers each carrier the beats its moments read — refusal and success on a gate, fired and journal on a trigger, offer and completion on a quest, offer and progress on an objective — and presents the trigger's pair honestly: `TriggerFiredEvent` rides referee visibility, so a trigger's `fired` text is table talk and its journal form is its player-facing voice. osrlib accepts unread beats silently, so a foreign document can arrive carrying text its carrier never reads; the editor's readout warns and names it rather than hiding it. The level form's ambient `guidance` slot (`SetLevelField`) is the same audience at level scope — per-level narrator steering, inert to the engine, read by narrator hosts the way a block's guidance field is.

**Diagnostics.** The validation tier picks up `validate_adventure`'s growth verbatim — dangling item, monster, area, level, and dungeon references in clauses, conditions, and consequences, selector violations, bundle collisions, `SetDoorState` sites naming no door, and whatever else the validator grows — parsed to addresses so findings click-navigate to the surfaces that own them (the address grammar grows item, trigger, and quest segments). The lint tier grows an advisory class, warning severity by construction — only `validate_adventure` gates publish, and nothing advisory ever escalates: flag reads with no writer (`flag_equals` or `flag_set` over a key no `SetFlag` writes — flag keys are an open domain osrlib deliberately leaves to authoring tools); trigger cycles (`SetFlag` feeding `flag_set` back into a loop the engine would truncate at its cascade bound, dropping the rest as notes); collision-prone trigger/encounter pairings (a spawn consequence aimed where a keyed encounter would already stand open drops at play); treasure rewards the award machinery will never price — granted items always value at zero under the engine's own XP-valuation rule, and a concluding quest's grants land after victory, where no return-to-town award ever runs — with no accompanying `AwardXP` (granted coins on a non-concluding quest price themselves at the return award and need no flag); and key-not-placed (a `has_item` gate on a bundled item — the ids the shop will never sell — that no cache holds and no consequence grants; a shipped id is purchasable and never flagged) — advisory forever, because trigger-granted items and random treasure make the general problem undecidable.

**Fences.**

- **Native projects only.** `overrides.yaml` has no authored-layer vocabulary — no items, no gates, no triggers, no quests. The gap is deliberate, recorded at [osr-forge#39](https://github.com/mmacy/osr-forge/issues/39), and growing the vocabulary is forge's decision — no shim here. In a forge-backed project the item and quests surfaces disable with an affordance explaining why, and every op carrying authored-layer content — the item, trigger, and quest ops whole, `SetLevelField` (no override kind carries level guidance), and an edge or transition batch whose value carries `requires` — blocks in place with the detach offer, the standing rule for ops without an override kind; each phase ships its ops with their blocks.
- **Additive against `schema_version` 3, no migration.** A pre-authored-layer document opens unchanged, normalizes once on its first write under the raised floor — the standing older-engine rule; the new empty keys and the re-stamp are one honest diff — and canonical-serialization byte-stability holds from then on.
- **Content packs are untouched.** Entries carry area content and geometry never copies, so gates stay behind with their doors and transitions; a pack-carried trap cannot carry a gated slide (unrepresentable in osrlib); triggers and quests are adventure-scope, outside the entry shape — growing the pack schema is osrlib's decision, taken if demand strikes. A dropped cache whose item ids resolved against the source's bundle dangles in the target: the standard diagnostics posture, legal while editing, gated at publish.
- **The editor never registers the `Interpreter`** and never simulates a firing: authoring is data, verification is play — publish to osr-web — and in-editor simulation is walk mode's backlogged territory.

## Forge-backed editing

The correction loop, graphical: open a workdir and the editor shows the assembled draft on the map, the report beside it, and the source pages behind it.

- **Review queue** — `report.json` flags rendered as a work list: per-area confidence, `geometry_synthesized`, `monster_unresolved:<name>`, `monster_custom`, `connection_ambiguous`, `transition_guessed`, `treasure_unparsed`, `page_unreadable`, and module-scope flags. Selecting a flag navigates to the area with its `source_pages` rendered alongside (the workdir's `pages/*.png`), so correction happens against the printed page. SVG previews are available for eyeballing whole-level geometry.
- **Edits are overrides.** Every committed batch translates to `overrides.yaml` entries — `areas:` field replacements, area add/remove, `geometry:` (cells, edges, entrance, transitions), `monsters:` remaps, `monster_templates:` patches, and town/module metadata — then re-assembles and refreshes the report. Forge's rules are honored mechanically: every entry must take effect (assembly failures surface with the failing entry), monster keys normalize the way forge normalizes them, area adds carry the required name/description/cells, and the `monsters:`-vs-`monster_templates:` exclusivity is enforced at edit time rather than discovered at assembly.
- **Map correction is the flagship case.** Forge's own spec expects synthesized geometry not to match the printed map; redrawing rooms, walls, doors, and transitions on the graph paper — or importing a level drawn in a scratch project — writes `geometry:` entries, no detach required. The translation is a diff against the deterministically recomputed synthesized geometry: forge merges overrides *over* it per canonical key, so the editor emits explicit `wall` entries sealing every stale synthesized opening, and a level import emits `areas:` adds alongside the geometry. Two residues are documented behavior, not bugs: freed corridor floor remains floor (forge has no corridor-removal override), and level dimensions are derived (the bounding box of the final plan), so a forge-backed level never shrinks below the synthesized floor plan's extent — a truly clean-slate map is what detach is for.
- **Reasons** — every override entry carries a `reason`. The editor auto-drafts one from the op ("room 7 cells redrawn to match p. 14") and the corrections panel lists every entry with its reason editable, because the file remains the human-readable, git-reviewable record forge designed it to be. Successive edits to the same address merge into its single entry (forge allows one per address, duplicate keys rejected), and the auto-drafted reason is latest-wins — the corrections panel is where a human composes a better one.
- **Undo** in forge-backed mode is snapshots of `overrides.yaml` — the document is derived state.
- **Stage controls** — run `check`, regenerate previews, and `rerun <stage>` with `--set` knobs from a pipeline panel showing `run.json` per-stage status and token usage; the knob→owning-stage guard is forge's, surfaced with its remedy.
- The general rule: any op whose translation has no override kind blocks in place with the detach offer — `WanderingSpec` changes, adding or removing a dungeon or level, renaming dungeon or level ids, `ResizeLevel` (dimensions are derived state in forge-backed mode), bundling a monster the module never mentions.

## Conversion

In scope from 1.0: the editor is the front door to the pipeline, not just the back office.

- **New from PDF** — pick a PDF, pick or confirm the provider, and the editor runs `osrforge.estimate()` first, presenting the page count and rough cost as a confirmation gate (the forge spec's intended host behavior).
- On confirm, the chain runs on a worker thread with `on_progress` streamed to a progress view — stage transitions, token usage, per-stage status. The confirm resumes rather than restarts: `estimate()` runs the real `preprocess()` into the workdir and leaves it warm (the licensing invariant forbids persisting module text anywhere else), so the editor calls `rerun(workdir, Stage.SURVEY, provider, …)` and never `convert()`, which would re-render every page. Cancellation is cooperative and takes effect at the next stage boundary, so completed stages persist (forge's own resume semantics) and `rerun` picks up where it stopped; the editor never hard-kills mid-stage, which is what keeps `run.json` consistent. Declining the confirm needs no cleanup: the warm workdir is honestly resumable and opens into the pipeline view. On success the project opens directly into the review queue.
- **Provider configuration** reads the same environment the forge CLI reads (Foundry endpoint, deployment, key or Entra ID). A settings panel shows detected provider status and lets values be set for the session; secrets are never written to editor config on disk.

## Validation and publishing

- **Live diagnostics** are always on (see the document service).
- **Publish to osr-web** — with a configured osr-web checkout, publish places the stamped document in its `adventures/` directory (symlink to the project by default, so saves republish live; copy as the alternative). Publishing gates on content validation passing; lint warnings prompt but don't block (secret-only access is sometimes the point). Export writes the stamped JSON anywhere.

## Authoring aids

All three ship in 1.0; all three apply their results as ordinary op batches (undoable, editable, no special state):

- **SRD stocking** — roll room contents for an empty area, or sweep a level's empty areas, through osrlib's stocking procedure over its shipped stocking, unguarded-treasure, and encounter tables, driven by a seeded RNG recorded in the sidecar (re-roll advances it; results are reproducible). The rules procedure is osrlib's — grown there as an additive release when this phase became its first consumer; the editor owns seed persistence, choosing targets, and applying results as ordinary op batches.
- **Treasure and encounter preview** — sample what authored content actually yields: N example hoards for a treasure-type letter via osrlib's generator, rolled counts and a stat summary for an encounter. Pure preview; never mutates the document.
- **Prose assistant** — optional, model-backed drafting of area descriptions and hooks from the authored facts (name, encounter, features, treasure, adventure tone), through the same `ModelProvider` interface and provider configuration as conversion. Suggestions are inserted only on explicit accept, token usage is displayed, and the feature is absent (not broken) when no provider is configured.

## The adventure planner

Sizing and pacing, made arithmetic. The planner answers "how much dungeon does this party need?" before a single room exists; the budget audit answers "is this dungeon on track to deliver it?" while the rooms fill. Both are advisory by construction — a pacing delta is a referee's judgment call, not a defect — so neither ever gates an edit or a publish, and the audit renders in its own panel rather than growing the diagnostics contract an advisory tier.

**A plan is a pure function of its inputs**, derived through four stages, each a knob cluster:

1. **Goal → XP pot.** The party as classes and counts with current XP, plus a target level. The pot is the XP still owed per character against each class's own progression — `load_classes()` is the authority — and the per-class divergence is surfaced, not averaged: the planner names the binding character ("the elf is the constraint; the thief levels at 30% of this pot"). Prime-requisite modifiers (`xp_modifier_pct`) and retainer half shares are knobs on the pot.
2. **Pot → sources.** The split across treasure, monster, and quest XP.
3. **Sources → depth.** Dungeon levels × rooms per level, an escalation curve across depth, and a hit-dice band per level.
4. **Pools → primitives.** Per level: encounter count and monster-XP pool, hoard count and expected-gp pool, trap and special counts, and quest milestones with XP values — the stocking brief a referee keys against.

**Baselines are sampled, never restated.** The defaults behind stages 2–4 — what share of yield treasure carries, how many rooms hold monsters, what a hoard is worth at depth 3 — are not constants in editor code: the planner derives them by running osrlib's own procedures under a recorded sample seed — `stock_area` per level band for densities and expected yields, the treasure generators for per-letter and unguarded-band expected values. The live structural lint is this codebase's one sanctioned re-implementation; the planner deliberately declines to become a second — it restates no table and forks no rule, so when osrlib's tables move, the baselines move with them, and the recorded seed keeps every derivation reproducible — under the pinned osrlib, deliberately: an upgrade that moves the tables moves the targets with it. Knobs are departures from baselines, every default visible and turnable. Two defaults have no procedure to sample and are owned outright, admitted here the way the lint exception is admitted: the retainer half share is the rules text's table practice with no osrlib surface behind it — the engine's own award divides evenly among living party members — and the quest share's honestly sampled baseline is zero, since stocking yields no quest XP. Both are advisory knobs binding nothing at play.

**Variance is shown, never hidden.** Gold-as-XP hoards swing wildly, so every treasure figure is an expected value with a sampled spread, and the suggestions carry theirs: treasure-letter combinations whose expected value lands a level's gp pool, and encounters drawn from the effective catalog inside the level's hit-dice band, XP-priced. Suggestions are advisory lists — nothing the planner or the audit produces ever applies to a document.

**Quest milestones are budget line items** — a name and an XP value, badged as referee-awarded. Authoring them into the document is the quest surface's work (see the authored layer); budgeting them is not blocked by it.

**The plan artifact.** `PlanSpec` is an editor-owned pydantic model — planning intent is editor metadata, never game content, so no osrlib schema grows for it. Only inputs persist: party, goal, knobs, and the sample seed; the derivation re-runs wherever the plan lands. The planner opens from the home screen with no project (last inputs remembered in app config) and inside any open project; export renders the Markdown stocking brief to any path, and adopting stores the `PlanSpec` in the open project's `editor.json` — both project types, since the sidecar is the one editor file a workdir carries. Adoption and rescale ride the sidecar's unguarded channel by the stash's own owner sanction — planning metadata, not the deliverable — sit outside document undo, and replace any previously adopted plan whole: the sidecar keeps no plan history, and git remains the cross-session net.

**The budget audit** is a read-only rollup over the working document, per level and whole-adventure: expected monster XP over keyed encounters; expected treasure value with spread through the same seeded sampling, with the lair accounting done right — the encounter's `hoard` toggle and the carried-versus-lair split via `plan_treasure_ref`, so a keyed monster's own treasure counts once and only when it would generate; treasure-cache coins and valuables at face value and items at zero — the engine's own XP-valuation rule, not an editor judgment; magic-item counts; stocked/empty and density ratios; and hit-dice-versus-depth outliers. Wandering encounters price at zero — unbounded by nature. A document that carries `Adventure.quests` (a converted or foreign module, or the authored layer's own phases) has its `AwardXP` rewards counted; `@party` awards need a party size and take the adopted plan's, or the audit panel's own party-size control when no plan exists — panel state, like the preview panels' own controls — while an `@first` award counts once, one recipient by rule. With an adopted plan the audit reads as per-level deltas against it; without one it reads as absolute yields. And when the map's real room counts differ from the plan's — the One Page Dungeon workflow guarantees they will — the audit offers a one-click rescale of the adopted plan to the rooms that exist: the plan refits the map, never the reverse.

## Design language

Graph paper and pencil — the drafting table these modules were born on:

- The aesthetic is scoped where it earns its keep: the map pane is literal graph paper — cream field, fine grid, pencil-weight walls, classic glyphs. The chrome around it is quiet, conventional tooling built from the component library, sharing the palette and type voices but never cosplaying as paper; the map reads as the artifact.
- Dark mode is graphite-on-slate — same language, inverted values — honoring `prefers-color-scheme`.
- Three type voices, matching the family convention: a humanist sans for UI, a serif for module prose (descriptions read as they'd be read aloud), monospace for dice, ids, and mechanics.
- All UI strings are sentence case.
- Red is reserved for destructive actions and errors; validation warnings use the pencil palette.

## Configuration

- App config via `platformdirs` (recents, osr-web checkout path, per-field picker locations, the planner's last inputs, UI preferences). No secrets on disk; provider credentials come from the environment.
- CLI: `osr-editor [PATH] [--port 8630] [--no-browser]` — serve, open the browser to the home screen (recents, new adventure, open project or workdir, convert PDF), or straight into the project at `PATH`. Default port 8630 (osr-web convention-adjacent, non-colliding).
- **Naming a path.** Every field that names a filesystem path — the project, workdir, PDF, import, export, and checkout fields alike — takes a typed path or a browse through the read-only directory listing, and `~` expands on all of them, the CLI's `PATH` included. Expansion happens once, in the request models, so no handler ever meets a tilde; the picker hands back the home-shortened form, which is a path those models accept verbatim. The picker never validates — a destination that does not exist yet is the normal case for half these fields — so refusals stay with the routes that consume the path.
- **Pickers are sticky, per field.** Choosing records the directory the picker was standing in, keyed by the field's own id, so the export picker reopens where you keep exports and the project picker where you keep projects. The record lives in app config and survives a restart; it is a convenience cache, capped and shape-validated because the keys come from the client, and a location that has since vanished needs no special case — the browse walks up to its nearest existing ancestor. Precedence on open: the field's own value, then the remembered location, then home.

## API surface

All under `/api`, JSON, localhost only. Representative, not exhaustive:

```text
GET  /fs                              # browse a directory (the path pickers)
POST /fs/location                     # remember where a field's picker last chose
GET  /projects                        # recents + detected type
POST /projects                        # create native project
POST /projects/open                   # open by path (native or forge workdir)
GET  /projects/{id}                   # document, revision, diagnostics, report (forge-backed)
POST /projects/{id}/ops               # atomic op batch @ revision → revision, delta, diagnostics
POST /projects/{id}/undo | /redo
POST /projects/{id}/publish | /export
GET  /catalogs/{monsters|equipment|spells|classes|tables}
POST /projects/{id}/aids/{stock|preview|prose}
POST /planner/derive | /planner/brief # plan derivation (no project); Markdown brief export
GET  /projects/{id}/audit             # expected-yield rollup + adopted-plan deltas
POST /projects/{id}/plan              # adopt or rescale a plan into the sidecar
POST /sources/open                    # read-only content-library source: a project or a pack file
POST /projects/{id}/packs/save        # save the stash or an entry selection as a content pack
POST /projects/{id}/forge/{assemble|check|rerun|detach}
GET  /projects/{id}/forge/pages/{n}   # workdir page image
POST /conversions                     # estimate → confirm token → run
GET  /conversions/{id}                # progress poll
```

Error conventions follow the family pattern: structured rejections for editing conflicts (409 on stale revision), 422 for malformed requests, osrlib/forge typed errors mapped with their remedies attached.

Every route resolves its caller through one FastAPI auth dependency whose shipped implementation returns the single local user unconditionally. It exists so a hosted future changes one function, not every handler; no other code assumes there is exactly one user.

## Technology decisions

- **Python ≥ 3.14** (the ecosystem floor), `uv`, `ruff`, `pyright`, `pytest`.
- **Dependencies:** `osrlib` (`>=1.3,<2`; phase 11 raises the floor to the release that grows `content_pack`; phase 14 raises it to `>=1.6,<2` — 1.5 grew gates, triggers, and quests, 1.6 their objective display names, and osr-web's adoption proved the model needs 1.6 — so the audit can count authored quest rewards, retiring in the same change the interim git-rev source pin, a stopgap from before osrlib published to PyPI now that 1.4.0 through 1.6.0 all publish), `osr-forge` (`>=0.1,<0.2` — 0.x pin, additive-artifact fence noted), `fastapi`, `uvicorn`, `pyyaml`, `platformdirs`. Dev-only: the node toolchain (React, TypeScript, Vite, Tailwind CSS, shadcn/ui as vendored source, vitest, Playwright). During development, sibling checkouts wire in as editable path sources per family practice; published builds pin PyPI ranges. The forge bridge also uses forge's module-level `rerun` (`osrforge.convert.rerun`) and preview regeneration (`osrforge.assemble.render_previews`), which sit outside its five-name facade by forge's own design — forge pins the facade list as fixed and does not grow it, so these stay stable module-level imports rather than facade promotions, and the 0.x pin contains the interim risk. (The phase 5 research corrected an earlier expectation here that forge would promote them; no such task exists on forge's side.)
- **Package** `osr-editor`, import `osreditor`, console script `osr-editor`. PyPI name availability is verified in phase 0; if taken, `osredit` is the fallback, decided then without ceremony.
- **The wheel ships the built frontend** in `src/osreditor/static/`; a build hook (or release CI step) runs the Vite build. Users never need node.
- **License** MIT. The editor ships no game content — osrlib carries the OGL data; the release audit machine-checks the dist like forge's does.

## Testing strategy

- **Backend unit tests (pytest):** op application and rejection per invariant, undo/redo, canonical-serialization byte-stability (write → reopen → no-op → write, byte-identical, for documents the editor wrote under the pinned osrlib), lint findings against fixture adventures (asserting parity with forge's finding ids on shared cases), op→override translation goldens, override reason drafting, content-pack stash and pack-file round-trips with source opens across project types, publish gating.
- **Round-trip fixtures:** original, editor-authored adventures committed as fixtures — a small complete module and a doors-and-transitions torture case — exercised through open, edit, undo, save, validate. No retail-derived document is ever committed (the licensing fence in `AGENTS.md`); sibling-checkout documents like osr-web's bundled B3 may be opened in local development testing but never enter the repository.
- **Forge integration:** the full forge-backed loop (open workdir → edit → assemble → check) against `FixtureProvider`-recorded workdirs; conversion progress plumbing tested the same way, zero network.
- **Frontend unit tests (vitest):** the edge-key math mirror, gesture reducers (rectangle → op batch), map hit-testing, the content-library drop mappers (carried-kind ops, collision handling, template closure and re-minting).
- **End-to-end (Playwright):** the core loops as smoke — create adventure, draw a room and corridor and door, key an encounter from the catalog, validate clean, export; open a fixture workdir, correct a flagged area, see the override written and the report refresh.
- **Compatibility:** golden `adventure.json` outputs are loaded against the pinned osrlib in CI (forge's discipline), so an osrlib upgrade that shifts document semantics fails loudly here first.
- **CI:** ruff, pyright, pytest, generated-type drift check, tsc, vitest, eslint, Playwright smoke.

## Future extensions

Named so the systems around them grow the right seams — these are directions, not commitments. Features cut from this spec and deferred indefinitely live in `backlog.md`, which is a record, not scope:

- **Stock-to-budget.** With a plan adopted and the audit reading deltas, the obvious next step is generation that lands inside tolerance: seeded re-rolls selected until a level's expected yield meets its target, or a One Page Dungeon generated to the plan's shape and stocked on arrival. Direction, not commitment — and fenced from birth: whatever drives the dice, the stocking procedure stays osrlib's, so the automation is selection among honest rolls, never a bespoke optimizer wearing the dice as a costume.
- **Map-format converter plugins.** The `GeometryImporter` entry-point seam ships in 1.0 and Watabou's One Page Dungeon rides it in phase 8. Formats beyond those two are built as demand strikes, and the bar decides where one lives: a converter is **bundled** when its format is broadly useful, permissively licensed, and parseable with no new dependency, and is a **separate installable package** otherwise. The entry-point group is public either way — the built-in importers register through the same group any third party uses, so the third-party path is exercised rather than merely promised, and no converter needs the editor's permission to exist. Candidates as demand strikes: Dungeon Scrawl, donjon, Dungeondraft.
- **A pack editor.** Content packs (phase 12) are composed by selection — save rooms from any open source as a pack. A dedicated surface for authoring a pack without a host adventure (a monster anthology, a trap collection built from nothing) waits for demand; the pack schema and the library panel are the seams it would build on, and nothing about them assumes a pack was born from a project.
- **Hosted deployment.** The auth dependency and the `ProjectStore` protocol are the two seams; nothing else assumes locality.
- **Party and pregen authoring**, as scoped in the non-goals — contingent on the ecosystem growing a pregen surface.

## Roadmap

Each phase ends with working, tested, documented software.

**Phase 0 — scaffolding and contracts.** Repo layout, uv + node toolchains, CI, FastAPI and Vite skeletons wired together, pydantic→TypeScript type generation with the drift gate, canonical serialization, stamped-document round-trip on an original fixture (write, reopen, no-op save, byte-identical), PyPI name verification. The revision/ops/diagnostics envelope, the auth dependency stub, and the `ProjectStore` protocol are locked here so every later surface obeys them from birth.

**Phase 1 — projects and prose.** Home screen, native project create/open/recents, the document service with undo/redo and live diagnostics, adventure/town/hooks/level-scope forms. Milestone: create a native project, edit its metadata and town, see content validation react live, export a stamped document osr-web lists.

**Phase 2 — the map editor.** The graph-paper canvas and the full tool set: rooms, corridors, edges and doors, areas, entrance, transitions, multi-level and multi-dungeon management, lint live on the map, and the `GeometryImporter` protocol with import-from-project as its first implementation. Milestone: author a two-level dungeon's complete geometry from a blank grid, lint clean, and play its empty halls in osr-web.

**Phase 3 — keyed content.** The map-first stocking flow — context menu, keyed-entry cards, stocking badges with next-unstocked navigation, type-ahead pickers — over the full content surface: encounters, features, traps, treasure, wandering. Milestone: hand-author a small complete adventure — keyed encounters, a trapped treasure cache, a secret door — publish it, and play it through in osr-web.

**Phase 4 — the monster editor.** The full stat-block surface: create, clone-and-modify, bundled-template management, collision handling. Milestone: a bespoke monster authored in the editor is encountered and fought in osr-web.

**Phase 5 — forge-backed projects.** Workdir open and detection, the review queue over report flags with source pages and SVG previews, op→override translation with reasons, the assemble/check loop, stage controls with rerun knobs, detach. Milestone: take a real converted workdir from flagged draft to publishable entirely in the GUI, with `overrides.yaml` as the reviewable record.

**Phase 6 — conversion.** New-from-PDF: provider settings, estimate and cost confirmation, the conversion chain on a worker thread with live progress and cooperative cancellation, landing in the review queue. Milestone: PDF to published adventure without touching the CLI.

**Phase 7 — authoring aids.** SRD stocking with seeded re-rolls, treasure and encounter previews, the prose assistant behind provider detection. Milestone: stock a blank level from the SRD tables, punch up its descriptions with the assistant, and publish.

**Phase 8 — external map import.** The first converter over the `GeometryImporter` seam: Watabou's One Page Dungeon JSON, with its door cells resolved onto edges, its keyed notes onto areas, its entrance-relative coordinates normalized, and every judgment call flagged — plus the metadata adoption phase 2 deferred to exactly this converter. Milestone: generate a dungeon at Watabou's generator, import it into a blank project, adopt its title and story, stock and publish it, and play it in osr-web.

**Phase 9 — documentation and release.** Docs site (mkdocs-material), README, packaging audit, tag-driven trusted publishing, PyPI release as `osr-editor` 0.1.0 (Development Status :: 4 — Beta), matching the family's release engineering.

**Phase 10 — screenshots in the guides.** The published guides show the real editor: an automated Playwright capture harness over the existing zero-network fixtures, light and dark, with the images committed and a CI job that fails when a shot can no longer be produced. Milestone: a reader who has never launched the editor sees every surface the guides describe, and a UI change that would strand a screenshot fails the build instead of shipping a caption that lies.

**Phase 11 — the content library.** Over an additive osrlib release growing the `content_pack` document kind (the editor as first consumer, the SRD-stocking precedent): the pack model as the library's internal currency, the read-only panel over derived packs (any project) and the embedded stash, drops that write what the entry carries with per-kind collision prompts and template closure, wandering-table copy, sidecar drop provenance with used badges, and the stash offer on replace-mode imports and clear level content. Milestone: stock a fresh OPD-imported project entirely by dragging rooms across from a converted module, then swap a new OPD map into one of that project's levels and re-place its displaced content from the library — both published and played in osr-web.

**Phase 12 — content packs.** The standalone pack surface over phase 11's model: saving the stash or any entry selection as a stamped pack file with computed template closure and authored metadata, opening pack files in the library panel, and monsters-only packs feeding one-click template adoption. Milestone: a pack of rooms and bespoke monsters saved from one project stocks a dungeon in a different project — the file is the hand-off a friend would get — published and played in osr-web.

**Phase 13 — the adventure planner.** The planning surface and the plan artifact: the party model over `load_classes()` progression with the binding-character callout and the prime-requisite and retainer knobs, the four-stage derivation with baselines sampled from osrlib's stocking procedure and treasure generators under a recorded seed, per-level targets with expected values and spreads, treasure-letter and encounter suggestions, quest milestone line items, the Markdown stocking brief, and plan adoption into the sidecar. Every osrlib surface consumed already sits inside the current pin — no floor change. Milestone: from the home screen, plan a three-level dungeon that levels a seven-character party to 2, read which character binds the budget, turn a knob and watch the plan re-derive, export the brief, and adopt the plan into a fresh project.

**Phase 14 — the budget audit.** The rollup over the working document: expected monster XP and treasure value with the lair-hoard split, density and hit-dice-band readouts, quest-reward counting — raising the osrlib floor to `>=1.6,<2` and retiring the git-rev source pin, which regenerates the types and puts the whole authored-layer schema in front of phases 15–17, and lets the open-fields guard stop warning on quest-bearing documents by construction — the per-level deltas against the adopted plan, and the room-count rescale after a geometry import. Milestone: stock the planned dungeon — SRD sweeps plus hand keying — and watch the audit's deltas converge on the plan; swap in an OPD map whose room count misses the plan and rescale; publish and play in osr-web.

**Phase 15 — bundled items and gates.** Over the raised floor: the item editor as a nav section mirroring the monster editor — the four template kinds, clone-from-catalog, collision refused at commit against equipment, magic, and bundle exactly as `validate_adventure` rules — with the item-template ops, every item picker moved to its site's true domain, the condition builder and the narrative-block editor in their full shapes (gates their first consumer), the level form's guidance slot over `SetLevelField`, gate cards on the door inspector and the transition dialog with map badges, forge-backed blocking for this phase's ops and `requires`-carrying values (each later phase blocks its own on arrival), and validation-tier addresses for items and gates. Milestone: author a key as a bundled item, cache it in room 1, gate a door on carrying it with authored refusal and success text, gate a transition on a toll that consumes — published and played in osr-web, the door refusing until the key is found.

**Phase 16 — triggers.** The quests panel joins the nav, its trigger surface first: the trigger list preserving document order with reorder ops, the pattern builder over all seven kinds, trigger conditions (consume-free by construction), the consequence builder over the closed nine-command union with selector-only recipients, the fired and journal voices in the narrative editor, area and level triggers placed from the map the way transitions are with glyphs at their addresses, `SetDoorState` consequences picking their door on the map, and the first advisory lints — flag reads with no writer, trigger cycles, collision-prone trigger/encounter pairings. Milestone: the lever-opens-portcullis pairing — a flag-setting lever trigger and a flag-gated door — authored from the map, published, and played in osr-web.

**Phase 17 — quests and the advisory battery.** The quests panel completes: the quest builder — activation clause or standing charge, objectives with display names, hidden/reveal, and completion clauses, rewards over the same consequence union, `all`/`any` completion, `concludes_adventure` — quest and objective narrative beats that journal as themselves, the remaining advisory lints (treasure rewards with no accompanying `AwardXP`; key-not-placed, advisory forever), and the audit's quest counting now reading rewards this editor authored. Milestone: author a winnable adventure — a fetch quest whose objective matches the idol's catalog id, activation on entering the dungeon, rewards that grant and award, `concludes_adventure` set — publish it and play it in osr-web to the victory screen.
