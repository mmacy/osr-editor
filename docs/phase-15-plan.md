# Phase 15 plan — bundled items and gates

Implementation plan for phase 15 of [the osr-editor spec](spec.md). Phase 15 opens the authored layer: the item editor as a nav section mirroring the monster editor — the four template kinds, clone-from-catalog, collision refused at commit against equipment, magic, and bundle exactly as `validate_adventure` rules — the item-template ops, every item picker moved to its site's true domain, the condition builder and the narrative-block editor in their full shapes with gates as their first consumer, gate cards on the door inspector and the transition dialog with map badges, the level form's guidance slot over `SetLevelField`, forge-backed blocking for this phase's ops and `requires`-carrying values, and validation-tier addresses for items and gates. Milestone: author a key as a bundled item, cache it in room 1, gate a door on carrying it with authored refusal and success text, gate a transition on a toll that consumes — published and played in osr-web, the door refusing until the key is found.

Phase 15 lands before phases 13 and 14, by owner decision — the adventure planner and the budget audit are picked up later. The precedent is phase 4 landing after phase 5: the resequencing is recorded in the plan, the spec stays untouched, and the one dependency that crossed the gap moves with the work that needs it. Here that dependency is the osrlib floor raise the spec assigns to phase 14 — `>=1.6,<2`, the git-rev source pin retired, the types regenerated, the open-fields guard silenced on authored-layer keys by construction — without which nothing in phases 15–17 exists in the schema. This phase carries it as work item 1; when phase 14 is planned, its floor-raise clause is already satisfied and its remaining scope (the audit itself) is unaffected.

Ten research facts shape this plan more than any others, each verified against the trees rather than recalled:

1. **The floor raise is the foundation and the blast radius.** The pinned rev (`pyproject.toml:86`, a 1.4-era commit) has `SCHEMA_VERSION = 2`; osrlib 1.6.0 has `SCHEMA_VERSION = 3` and stamps `engine_version` 1.6.0 (`osrlib/versioning.py:30,73`). Raising the floor therefore re-stamps every document the editor writes and regrows every serialized payload: `Adventure.model_dump` gains `items`, `triggers`, and `quests` at top level (`osrlib/crawl/adventure.py:130-132`), every level gains `guidance: ""` (`osrlib/crawl/dungeon.py:556`), and every door and transition gains `requires: null` (`dungeon.py:209,253`) — the spec's "one honest diff," after which canonical byte-stability holds again. Every committed fixture regenerates through its existing script. The open-fields guard (`documents.py:266-312`, produced at `projects.py:236-249`) stops warning on authored-layer keys with no code change — the keys are in the pinned model now. One posture to record rather than code around: osrlib has no adventure-kind migration — `MIGRATIONS` is save-shaped (`osrlib/persistence.py:82`), and the schema-3 trap-trigger repair for content packs lives in osrlib's own pack loader (`osrlib/crawl/content_pack.py:103`) — so a foreign schema-2 document carrying the dead `kind="treasure"`/`trigger="enter"` combination fails open with the model validator's message. Editor-authored documents never carry it (the editor stopped offering the combination before any shipped), no fixture does, and the editor does not fork a repair. Retirement mechanics: floor to `osrlib>=1.6,<2` (`pyproject.toml:32`), delete the `[tool.uv.sources]` block and its stale comment (`pyproject.toml:80-86` — its own text says "swapped for the plain PyPI range when a release with this surface publishes"; 1.4.0 through 1.6.0 all publish now), `uv lock`. No resolver conflict: osr-forge pins `osrlib>=1.2,<2`. osr-web's adoption is merged and pins `>=1.6`, so the milestone's played half is real.
2. **Gates ride existing ops as values — no new gate op exists or is needed.** `SetEdges` embeds osrlib's `Edge` whole (`ops.py:237-255`) and `AddTransition` embeds `TransitionSpec` whole (`ops.py:436-449`), so the regenerated types carry `requires` into the op surface transitively and the batch's mandatory re-validation (`documents.py:605`) enforces model validity as always. The forge fence therefore becomes value-dependent, and `ensure_forge_supported` already has two value-dependent branches to model the new ones on (`overrides.py:192-203`); `translate_batch`'s closing `AssertionError` backstop (`overrides.py:373`) forces every new op to be either translated or blocked, so nothing can slip through untranslated. A gated trap slide is unrepresentable at request parse — `TrapEffect` rejects a transition carrying `requires` (`dungeon.py:303-306`) — so the trap builder's transition sub-form needs no gate control and gets none.
3. **The gate model, exactly** (`osrlib/crawl/gates.py`): `GateSpec` is one condition plus an optional `NarrativeBlock` (`gates.py:109-120`) — one condition per gate, not a list. The condition union discriminates on `condition_type` over exactly three kinds (`gates.py:100-106`); `consumes` is a field of `HasItemCondition` alone (`gates.py:64-66`) — the other kinds have nothing to take, so no generic "consumes" control can exist. `FlagEqualsCondition.value` is `str | int | bool` compared strictly through `flag_values_equal` (`gates.py:167-194`: a stored `True` never satisfies an authored `1`), so the builder's value control must preserve type, never coerce. `EffectActiveCondition.kind` is a free string — an open domain, unchecked by design. A gate reads exactly two beats: `refusal` and `success` (`osrlib/crawl/exploration.py:1400,1426-1428`); `journal` is read only by the trigger interpreter (`osrlib/crawl/interpreter.py:361-362`). Every `NarrativeBlock` field defaults `""` — empty means unauthored, never `None` (`osrlib/crawl/narrative.py:84-102`). `requires` hangs on exactly two carriers: `DoorSpec` (`dungeon.py:209`) and `TransitionSpec` (`dungeon.py:253`).
4. **The item surface and its stricter rule** (`osrlib/core/items.py`, `osrlib/crawl/adventure.py`): four template kinds discriminated on `item_type` (`items.py:185,215,272,294`; the `ItemTemplate` union at `items.py:304-307`). The collision domain is equipment ∪ magic ∪ bundle — `_effective_equipment` seeds its seen-set from all four shipped lists *and* `load_magic_items()` (`adventure.py:214-217`), and `validate_adventure` emits `bundled item id {id!r} collides with the catalog` per collision (`adventure.py:524`). Cache `item_ids` now resolve against the *effective* catalog (`adventure.py:565-569` passes `effective_items` into `_validate_feature`), and gate conditions resolve against effective equipment ∪ shipped magic (`_dangling_condition_item`, `adventure.py:268-289`), emitted as `{owner}: door {edge_key} gate references unknown item {id!r}` and `{owner}: transition at {position} gate references unknown item {id!r}` (`adventure.py:583,586`). Two model validators carry form shape: missile quality ↔ ranges present together (`items.py:202-207`), and body armour (ac + ac_ascending + category) XOR shield (ac_bonus) (`items.py:226-234`). Item templates carry `overrides_applied` but no `page`.
5. **The monster editor maps one-to-one, and its every decision is already settled.** The op trio's shape (`ops.py:158-211`: whole-value grain, embedded osrlib model, first-match among foreign duplicates); the cached shipped-id set and `_require_monster_id_free` with the new-or-changed-only carry-through (`documents.py:1181-1211`, applied at `1221-1225` — a foreign colliding id never locks its document); the rename cascade with the honest whole-document delta (`documents.py:1245-1259`); the blocked-table entries and address branches (`overrides.py:135-148,151-171`); the full-template detail route for clone (`catalogs.py:177`, `app.py:1548`, the summaries-for-pickers/full-for-clone split pinned in `catalogs.py:1-21`); the section anatomy (`monsters-section.tsx`: list rows with reference counts and two-step remove at 254, `CloneSourcePicker` at 337, create dialog at 387, the inline `op_invariant` rename prompt at 419-428 and 533-539, the detail editor at 591, `AuthorNotesCard` at 231); the builder module (`monster-builders.ts`: seed at 72, `cloneId` at 118, compute-in-the-queue updates at 197); and the client-side effective catalog with bundled-first ranking (`catalogs.ts:71,118`). The item editor is that machine over four far smaller models.
6. **The raised floor obligates cascade completion.** The moment the pin moves, a foreign 1.6 document carrying triggers and quests opens and edits — with no trigger or quest authoring surface until phases 16–17, so a re-keying op that skips authored-layer reference sites would strand a reference its author cannot repair in the editor. The sites, from the 1.6 models `validate_adventure` walks (`adventure.py:316-469`): dungeon ids in `AreaEnteredPattern`/`LevelEnteredPattern`/`DungeonEnteredPattern`, `SetDoorState`, and `PlaceParty.location`; level numbers in the same minus `DungeonEnteredPattern`; area ids in `AreaEnteredPattern`; monster ids in `MonsterDefeatedPattern` and `SpawnMonsters`; item ids in `HasItemCondition` (gate or clause condition), `ItemAcquiredPattern`, and `GrantItem` — each site reachable from a trigger's `when`/`conditions`/`consequences` and from a quest's `activation`, each objective's `when` and `reveal_when`, and its `rewards`. Removals keep admitting dangling references (the diagnostics posture); only re-keys cascade, exactly as today.
7. **The diagnostics machinery is built for this growth.** `_OWNER_SHAPES` full-matches each check's tail after the `{dungeon} level {n}: ` prefix with enumeration-confirmed owners — never regex-extracted ids (`diagnostics.py:66-118`); the bundled-monster collision classifier renders each bundled id exactly as osrlib reprs it and degrades to the bare `monsters` scope when no distinct id confirms (`diagnostics.py:159-176`); and the `validation_unclassified` fallback carries any unrecognized line verbatim with `address=None` (`diagnostics.py:199`) — which is what absorbs trigger- and quest-error strings from foreign documents until phases 16–17 grow their addresses: visible, honest, never navigable lies. `addresses.py` holds the grammar builders; `navTargetFor` (`address.ts:88-140`) resolves `monsters` and `monster:<id>` with a not-bundled refusal — the exact pattern `items`/`item:<id>` mirrors.
8. **Today's item pickers are shipped-only, and no bundle-aware item surface exists anywhere.** The equipment picker searches `GET /api/catalogs/equipment` — the shipped lists alone (`equipment-picker.tsx`, `catalogs.py:200-213`) — and is used at exactly one site, treasure-cache `item_ids` (`area-content-cards.tsx:854`); the magic-item picker (PR #54) serves `magic_item_ids` beside it (`area-content-cards.tsx:860-898`). A grep for authored-layer vocabulary over `src/` and `frontend/src/` returns zero real hits, and the generated types carry no `ItemTemplate`, `NarrativeBlock`, or `requires` schema. The client-side merge precedent is `effectiveMonsterCatalog` (`catalogs.ts:71`: shipped ∪ bundled, bundled first, shipped-id collisions skipped).
9. **The level form and its op have prepared slots.** `_apply_level_field` already exists, typed narrowly over `SetWandering | SetEntrance`, returning the precise `/dungeons/{i}/levels/{j}/{field}` pointer (`documents.py:1331-1339`) — `SetLevelField` widens that union. The field-op shape to copy is `SetAdventureField`/`SetTownField` (`ops.py:107-155`: `field: Literal[...]` + value + a match guard). The UI slot is `LevelPropertiesDialog`'s field stack (`map-dialogs.tsx:507-593`, `WanderingForm` at 725-778), with the committed-field textarea precedent at `map-inspector.tsx:185-207`.
10. **The forge affordance split is the spec's own, reconciled with phase 4's teaching rule.** The authored-layer fence says the item and quests *surfaces* disable with an affordance explaining why, while every authored-layer *op* blocks in place with the detach offer. Phase 4's standing objection — a disabled control cannot open the dialog that teaches — is honored by making the affordance a live destination, not a dead tooltip: the Items nav entry stays present and clickable and navigates to an explanation body naming the deliberate overrides-vocabulary gap ([osr-forge#39](https://github.com/mmacy/osr-forge/issues/39)) with detach offered in place. Unlike monsters — where assembly derives a bundle worth reviewing — a forge-assembled document can never carry items, so there is no list to render and the explanation *is* the honest section body. Gate cards and the guidance slot sit inside surfaces that are otherwise live in forge mode, so they follow phase 4's offer-in-place posture exactly: flow-entry actions route to the blocked-op dialog client-side, and the server's 422 stays the authority for any batch that arrives.

## Work items

### 1. The floor raise

- `pyproject.toml`: `osrlib>=1.6,<2`; delete the `[tool.uv.sources]` block and its comment whole (osrlib is its only entry); `uv lock`. Development against a moving osrlib target is over — 1.6.0 is published and is the schema this phase authors against.
- Regenerate `frontend/src/types/generated/api.ts`. The authored-layer schema arrives transitively — `OpBatch` → `AnyEditOp` → `Edge`/`TransitionSpec` now carry `requires` → `GateSpec` → the condition union and `NarrativeBlock`; `ProjectState` → `Adventure` now carries `items`/`triggers`/`quests` → the four `ItemTemplate` kinds and the trigger/quest models. The drift gate and the `[ApiError]` injection list are unchanged.
- Regenerate every committed fixture through its existing script (`generate_documents_golden.py`, `generate_small_module.py`, `generate_torture_fixture.py`, `generate_forge_workdir.py`, and the OPD goldens if their outputs embed stamped documents): schema 3, engine 1.6.0, the new default keys. One honest diff per fixture; the byte-stability suite then re-proves stability under the new pin, and the golden-compatibility discipline covers the authored-layer keys from this phase forward.
- Behavior recorded, not coded: the open-fields guard stops warning on authored-layer keys by construction (research fact 1); a foreign schema-2 document carrying the dead treasure-trap trigger fails open with the model validator's message, and the editor forks no repair — osrlib owns migrations, and the adventure kind has none.
- The suites run green at this point, before any new surface — the raise is its own commit-able, verifiable step.

### 2. Cascade completion under the raised floor

A pure traversal in `documents.py` — one helper walking `adventure.triggers` and `adventure.quests` (a trigger's `when`, `conditions`, and `consequences`; a quest's `activation`, each objective's `when` and `reveal_when`, and its `rewards`) and rewriting one reference kind per call — wired into every re-keying op:

- `RenameDungeon` additionally rewrites pattern `dungeon_id`s, `SetDoorState.dungeon_id`, and `PlaceParty.location.dungeon_id` scoped to the renamed dungeon; `RenumberLevel` the level numbers of sites naming its dungeon and old number; `SetAreaField(field="id")` the `AreaEnteredPattern.area_id` of sites naming its dungeon, level, and old id; `SetMonsterTemplate` renames additionally rewrite `MonsterDefeatedPattern.template_id` and `SpawnMonsters.template_id`; `SetItemTemplate` (item 3) is born cascade-complete.
- When the traversal rewrites anything, the op's delta is honestly whole-document (`path=""`) — the `RenameDungeon` posture; when it touches nothing, deltas are unchanged.
- Removals stay dangling-by-diagnostics: `validate_adventure` already names every dangling clause and consequence reference, and the parser's fallback carries those lines verbatim (research fact 7).
- Tests build authored-layer adventures in-test (committed fixtures grow trigger and quest content with the phases that can author it) and assert each re-key rewrites each site kind, through undo and redo.

### 3. The item-template ops

New frozen ops in `ops.py`, adventure-scoped, the monster trio verbatim (research fact 5):

- **`AddItemTemplate`** — `template: ItemTemplate` (the discriminated union; the four kinds ride the wire on `item_type`). Appends to `Adventure.items` in authored order.
- **`SetItemTemplate`** — `item_id: str`, `template: ItemTemplate`: whole-value replacement; a differing `template.id` is a rename, cascading in the same commit over every in-document reference: cache `item_ids` on area and level features, `HasItemCondition.item_id` inside door and transition gates, and the authored-layer sites via item 2's traversal. First-match among foreign duplicate bundled ids.
- **`RemoveItemTemplate`** — `item_id: str`. Removal admits dangling: cache references become `feature_unknown_item` findings and gate references the new gate findings — legal while editing, gated at publish. The UI confirms first when references exist, naming the count.
- The collision invariant, `_require_item_id_free` beside its monster sibling: rejects an empty id, and a **new or changed** id present in the cached shipped-equipment ids (all four lists of `load_equipment()`), the cached shipped-magic ids (`load_magic_items()`), or the rest of `Adventure.items` — the exact domain `_effective_equipment` seeds (research fact 4), so the editor refuses at commit precisely what `validate_adventure` would flag. The carry-through rule holds: a foreign document's already-colliding id passes through untouched and stays a navigable diagnostic; the invariant is "no op ever *introduces* a collision."
- Application: `_apply_*` helpers rebuilding `Adventure.model_copy(update={"items": ...})` with delta pointer `/items` (whole-document on rename, per item 2). `_remap_rules` grows the rename rule remapping `item:<old>` note keys to `item:<new>`, riding the established cascade-and-undo machinery.

### 4. `SetLevelField` and the guidance slot

- **`SetLevelField(LevelOp)`** — `field: Literal["guidance"]`, `value: str`, the `SetAdventureField` shape; the `Literal` grows if a later osrlib adds level fields. Application widens `_apply_level_field`'s union (research fact 9), answering the precise `/dungeons/{i}/levels/{j}/guidance` pointer.
- The UI is one committed-field textarea in `LevelPropertiesDialog`, between the wandering form and the level features, labeled for its audience — ambient steering for a narrating front end, never shown to players verbatim — with `useCommittedField` and the standing one-batch-per-commit grain. It is steering, not read-aloud prose, so it takes the UI voice, not the serif.
- In forge mode the field routes to the blocked-op dialog on entry (item 5's client mirror), the server's 422 behind it.

### 5. Forge blocking

- `_BLOCKED_MESSAGES` grows four entries: the three item ops sharing "bundled item templates have no override kind — the overrides vocabulary has no authored-layer surface," and `SetLevelField` with "level guidance has no override kind." `_blocked_address` grows the matching branches: `item_address(...)` from the op's id, `level_address(...)` for the field op.
- `ensure_forge_supported` grows two value-dependent branches beside the existing two (research fact 2): a `SetEdges` whose values include an edge carrying `door.requires` blocks at that edge's address, and an `AddTransition` whose `transition.requires` is set blocks at its cell address — both with "gates have no override kind." An ungated batch translates exactly as before, and the batch-rejects-whole-before-any-side-effect contract is inherited, not rebuilt.
- The frontend mirrors: `BUNDLED_ITEM_BLOCKED_MESSAGE` in `lib/item-builders.ts` (the `monster-builders.ts:19` convention, mirrored verbatim from the server table); the Items section's forge affordance (item 8); the gate cards' add-gate action and the guidance field routing to the blocked-op dialog client-side so nobody authors a gate just to be refused — the server staying the authority.
- `translate_batch` is untouched: blocked ops never reach it, and its `AssertionError` backstop enforces that every new op took one of the two paths.

### 6. The catalog detail route

`GET /api/catalogs/equipment/{item_id}` answers the full `ItemTemplate` for a shipped id — the clone source, served from `load_equipment().get(...)`. Unknown id → 404 `catalog_item_not_found` (a new typed error beside `CatalogMonsterNotFoundError`, mapped like its neighbor). The list route's `CatalogItem` summaries stay picker-thin by `catalogs.py`'s own charter; bundled templates need no route — the document is in hand client-side. Magic items are not clone sources (a bundle is never magic) and get no detail route.

### 7. Addresses and diagnostics

- `addresses.py` grows `item_address(item_id) -> "item:<id>"`, a top-level segment beside `monster:<id>`; the bare `items` scope joins `monsters` as a coarse degrade target.
- `diagnostics.py` grows three classifications, all under the enumeration-confirmation discipline (research fact 7):
    - `bundled_item_collision` — a static-shape classifier mirroring `_classify_bundled_collision`: each bundled item id rendered exactly as osrlib reprs it into `bundled item id {id!r} collides with the catalog`, addressed `item:<id>`, degrading to `items`.
    - `door_gate_unknown_item` — the owner-scoped shape `door {edge_key} gate references unknown item {id!r}`, its edge key confirmed by rendering each of the level's edge keys into the line (the dangling item id is unconfirmable by definition and stays message text), addressed to the door's edge address.
    - `transition_gate_unknown_item` — `transition at {position} gate references unknown item {id!r}`, the position confirmed against the level's transitions, addressed to the cell.
- `feature_unknown_item`'s semantics follow osrlib's: the finding now clears the moment the named id joins the bundle — the `encounter_unknown_monster` behavior, proven by test.
- `address.ts`: the `items` scope and `item:<id>` map to a NavTarget opening the Items section, with the not-bundled refusal `monster:<id>` already models; the diagnostics panel and map markers need no changes beyond the new addresses resolving.

### 8. The Items section

A new always-present nav entry beside Monsters, `monsters-section.tsx`'s anatomy over four smaller models:

- **The list** — every bundled template: name, id and kind in monospace, cost, and a referenced-by count over every site the cascade covers (caches, gates, and any authored-layer references a foreign document carries). Header actions: "New item" and "Clone catalog item". Row removal is the two-step confirm; a referenced template's confirm states the count and that references become diagnostics.
- **Create** — a kind choice (weapon, armour, gear, ammunition) plus id and name over per-kind model-valid seeds, every value neutral or osrlib-derived: weapon — damage `1d6`, qualities `(melee)`, standard material, cost 0, weight 0; armour — the body triple `ac 9 / ac_ascending 10 / category light` (the unarmoured pair, the monster-seed convention), cost 0, weight 0; gear — cost 0, lot size 1, no capacity, no combat facet, empty params; ammunition — cost 0, lot size 1, weight 0, standard material. Editor-authored templates set `overrides_applied=()` (SRD-compiler provenance, meaningless here; carried through untouched on `SetItemTemplate` over a foreign template and never surfaced — items have no `page`).
- **Clone** — the `CloneSourcePicker` pattern over the effective item catalog: a shipped source fetches the full template through item 6's route, a bundled one reads the document. The id prefills next-free `<source-id>-<n>` over the **full collision domain** — shipped equipment, shipped magic, and bundle — so a prefill never lands on a rejection; the inline `op_invariant` claim renders the rename prompt, the phase 4 gesture.
- **The detail editor** — always-saved per gesture through `lib/item-builders.ts` (seed, clone, reference-count, and compute-in-the-queue update builders mirroring `monster-builders.ts`), one form per kind covering its whole model, shape carrying the validators: the weapon form's missile-quality toggle seeds a neutral ordered three-band `missile_ranges` on and clears it off in the same gesture (the AC-pair convention; `5'–50' / 51'–100' / 101'–150'`), damage on the dice convenience mirror with the server's parse as authority, qualities as a multi-select over `WeaponQuality`; the armour form's body/shield radio swaps the field sets whole (body seeds the triple, shield seeds `ac_bonus 1`) so the XOR is unrepresentable to break; the gear form offers cost, lot size, optional capacity, the optional combat facet as a disclosure (damage, qualities, ranges under the same coupling), and params as key/value rows with JSON-typed values (the monster-ability params precedent); the ammunition form is cost, lot size, weight, material. `AuthorNotesCard` keyed `item:<id>`, remapped on rename.
- **Forge mode** — the entry is present and navigates to the explanation body: the overrides vocabulary has no authored-layer surface, the gap is forge's recorded decision (osr-forge#39), and detach is offered in place (research fact 10). No list renders because no forge-assembled document can carry items.

### 9. The condition builder and the narrative-block editor

Two shared components, built here in their full shapes with gates as first consumer and phase 16's parameters designed in:

- **`ConditionBuilder`** — a kind select over the three-member union. `has_item`: an item picker over the gate domain (item 11) plus the consumes toggle, shown only when the host offers it (`offerConsumes` — gates true; phase 16's trigger and quest clause builders pass false and the control never renders, the unrepresentable rule made a prop) with the toll's semantics stated in its help text (taken from the first carrier in marching order, per success). `flag_equals`: a key input plus a **typed value control** — a segmented text/number/boolean choice whose committed value preserves its type end to end, because osrlib's equality is strict and a `true` that arrives as `1` is a different authored value (research fact 3). `effect_active`: a free effect-kind input, the open domain.
- **`NarrativeBlockEditor`** — the carrier declares its read beats; a gate's are `refusal` and `success`, and `speaker` and `guidance` render for every carrier (attribution and narrator steering are audience fields, not display beats). Non-empty beats *outside* the carrier's read set — a foreign block carrying `fired` or `offer` on a gate — warn by name with a one-patch clear as the offered repair: the room-trap-trigger posture, never silently rewritten, never hidden. A block whose every field is empty commits as `None` rather than an empty `NarrativeBlock`, keeping unauthored gates canonical; an arriving all-empty block is left alone until the card's next commit.
- Both live under `components/` with pure builders in `lib/`; their vitest suites are written against the props phase 16 will reuse, so the trigger work inherits tested components, not a refactor.

### 10. Gate cards and map badges

- **`GateCard`** — the shared card composing item 9's two components, with add/remove affordances: no gate shows "Add gate"; a gate shows the condition builder, the block editor, and "Remove gate".
