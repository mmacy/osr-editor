# Phase 11 plan — the content library

Implementation plan for phase 11 of [the osr-editor spec](spec.md). Phase 11 ships the third stocking mode: a read-only library panel that opens finished work as content packs — derived from any project, or embedded in the sidecar as the displaced-content stash — and drops geometry-free room entries onto the map, writing exactly the kinds each entry carries with per-kind collision prompts, template closure, wandering-table copy, sidecar drop provenance with used badges, and the stash offer on both bulk content-destroying acts. It rides an additive osrlib release growing the `content_pack` document kind, with the editor as first consumer — the SRD-stocking precedent. Milestone: stock a fresh OPD-imported project entirely by dragging rooms across from a converted module, then swap a new OPD map into one of that project's levels and re-place its displaced content from the library — both published and played in osr-web.

Twelve research facts shape this plan more than any others, each verified against the trees rather than recalled:

1. **Every op a drop emits already exists, and the forge posture costs zero backend code.** The drop vocabulary the spec names — `SetAreaField`, `SetEncounter`, `SetTrap`, `SetTreasure`, `AddFeature`, `SetWandering`, `AddMonsterTemplate` — is complete in `ops.py` (`ops.py:296,335,351,364,387,224,158`), and the forge translation table already draws the exact line the spec draws: area-scoped `AddFeature` translates (only the level-scope form is blocked, `overrides.py:198-203`), while `AddMonsterTemplate` and `SetWandering` sit in `_BLOCKED_MESSAGES` (`overrides.py:145,136`) and `ensure_forge_supported` rejects a batch whole *before any op applies or any side effect lands* (`documents.py:641`, proven at `test_overrides.py:556`), surfacing as 422 `op_unsupported_forge` which the store already routes to the blocked-op dialog with the detach offer (`project-store.ts:179-191`). So a closure-bearing drop or a wandering copy in a forge-backed target blocks in place exactly as specified, and a drop whose references resolve against the shipped catalog or the target's own templates translates clean — the mapper simply emits no `AddMonsterTemplate` when it reuses.
2. **osrlib has no document-kind registry, and `"adventure"` is not an osrlib kind.** `stamp_document`/`check_document` (`versioning.py:50,73`) treat `kind` as a bare non-empty string; the kinds osrlib mints today are `"character"`, `"party"` (`character.py:311,351`), and `"save"` (`persistence.py:130`), while `"adventure"` is stamped entirely by the editor (`documents.py:180,203`). `content_pack` is therefore the first *content-authoring* kind osrlib itself owns, and "registering the kind" means shipping the `to_document`/`from_document` pair beside the model — the character/party pattern (`check_document` → `model_validate`, `ValueError` wrapped into `ContentValidationError`, `character.py:332-336`), not an envelope change. Saves are the only kind that participates in `MIGRATIONS` (`persistence.py:65`), and they earned it by having a plain-dict payload; a model-payload kind rides the counter without touching the chain, which is exactly the deferral the spec pins ("phase 11's osrlib release carries only the models, the validator, and the kind"). Re-stamp-on-write is today an emergent property of `stamp_document` stamping current versions, written down only in the editor (`documents.py:9-12`); for packs osrlib must own it as documented behavior, since shared packs are the family's longest-lived artifacts.
3. **`validate_adventure` raises a joined string blob, and the editor already pays for that shape once.** It returns `None` and raises `ContentValidationError` with newline-joined f-strings (`adventure.py:148,221-222`); the editor reverse-engineers those strings through a fifteen-entry regex table its own docstring calls "deliberate, contained fragility" (`osreditor/diagnostics.py:66-85`). The pack validator's first consumer is a panel that lists findings, not a gate that wants pass/fail — so `validate_content_pack` returns a tuple of structured findings (empty means clean) instead of mirroring the raise-a-blob shape, reusing the dotted-snake-case code discipline osrlib's `Rejection` already pins (`core/validation.py:38-45`). "Beside `validate_adventure`" is placement and role, not signature; a second string-parser in the editor would be repeating a documented mistake.
4. **Every model a pack entry carries is already standalone-safe except `AreaSpec` — which is the point.** `AreaSpec.cells` is required with `min_length=1` (`crawl/dungeon.py:458`), the invariant the spec keeps out of the document by having the pack hold placeless rooms; so the entry is `AreaSpec` minus geometry — the same optional slots, no `cells` — with the one validator that lives on `AreaSpec` itself restated (`_trap_kind_matches`: an entry's trap must be `kind="room"`, `dungeon.py:464-468`; a feature's treasure-trap coupling rides inside `FeatureSpec` already). `KeyedEncounter`, `TrapSpec`/`TrapEffect`, `AreaTreasureSpec`, `FeatureSpec`, `WanderingSpec`, and `MonsterTemplate` reach for no catalog and no container; dangling `template_id`s are legal at model level (caught only by validation, `dungeon.py:394-420`), which is what lets a loaded pack dangle and still drop. Two edges to carry: `EncounterTable` demands exactly rows 1–20 (`tables.py:430-436`), so a pack's wandering tables are complete tables or absent, never partial; and `TrapEffect.transition` embeds a full `TransitionSpec` naming dungeon and level (`dungeon.py:252`) — the slide-trap case the spec names as legitimately arriving dangling.
5. **The sidecar's addressed-map machinery is built for exactly one more map.** `_remap_sidecar_keys` hardcodes the two maps it cascades — `notes` and `stocking.streams` (`documents.py:895-932`) — over the four re-keying ops' prefix rules (`documents.py:1023-1044`); the applied pairs ride `HistoryEntry.key_remap` and undo replays them inversely, redo forward, with the contract stated in the docstring: "the addressed *content* never rides the stack, only the keys" (`documents.py:317-334`). The parity suites assert key-for-key cascade across every rule and across undo/redo (`test_sidecar.py:175,190,372,431`). The copies map joins all three places or it drifts.
6. **`apply_stock` is the compound-act template the stash act copies.** One lock acquisition around the whole gesture, the stale-revision refusal *before* any side effect, sidecar mutation and `persist_sidecar` inside the same critical section, and a response wrapping an ordinary `OpBatchResult` the store consumes like any `/ops` answer (`documents.py:572-635`, `aids.py:196`). The stash act needs the same shape for a different reason: the capture must be computed against a verified revision so the pack records what the batch is about to destroy.
7. **Nothing opens a second project through `ProjectStore` today, and the pieces for all three derived-source branches exist separately.** The geometry importer reads a foreign `adventure.json` with a raw `Path.read_bytes()` (`importers/project.py:58-61`) and deliberately carries geometry and identity prose only (`importers/__init__.py:46-75`) — the spec's own boundary, and the reason the library is its content-bearing counterpart rather than an extension of it. The current-first branch exists: `DocumentService.open_at(path)` answers "is this path already open" with the shared in-memory `OpenProject` (`documents.py:425-439`). The forge branch exists: `open_workdir_state` assembles current-first and raises `ForgeWorkdirIncompleteError` naming the first incomplete stage (`forge.py:189-232`), the exact refusal-with-remedy the spec requires a source open to reuse — and assembly is pure and deterministic by forge's contract, so opening a workdir source is zero-network. What phase 11 adds is the seam-honest native read: `project_exists` + `read_artifact` through the store, the first true second-project consumer of the protocol (`store.py:70-147`).
8. **The frontend has no drag-and-drop anywhere, and the surrounding architecture picks the design.** Zero hits for HTML5 DnD or any DnD library across `frontend/src`; the canvas sets `touch-none` and captures pointers on down (`map-canvas.tsx:166,268`), and the one existing "pointer event → area resolution" precedent is the context menu's own `hitTest` + `areaAt` flow (`map-editor.tsx:840-895`). So entries are HTML5 drag sources in the panel, the drop target is the existing wrapper div around the canvas (`map-editor.tsx:861`), and `dragover`/`drop` resolve the area under the cursor through the same hit-test shape the context menu uses. The mapper follows the import precedent exactly: a pure function from entry + committed document + choices to one ordinary op batch (`import-mapping.ts:72-187`, committed through the store's builder form at `import-dialog.tsx:177-190`), with node-env vitest asserting op sequences (`import-mapping.test.ts:68-80`). The two remembered-choice precedents are `clearRemovesAreas` (session-sticky on the store, with the prompting-thirty-times rationale in its comment, `project-store.ts:59-65`) and `cardIntent` (panel-lifetime state with render-time invalidation, `map-editor.tsx:197,260-262`); per-pack collision memory is the second kind. The minting conventions the spec names already exist client-side: `nextFreeFeatureKey` over the level-wide union (`content-builders.ts:339-347`) and `cloneId`'s first-free `<id>-<n>` over the effective catalog (`monster-builders.ts:118-122`).
9. **The pack-source fixture already exists and already exercises closure.** `tests/fixtures/small_module.json` carries keyed encounters with dice and fixed counts, letters and unguarded treasure, a room trap, a trapped cache, a construction trick, a level-scope custom feature, an inline wandering table on level 2, and — decisively — a bundled bespoke monster template keyed in a level 2 encounter (`test_small_module.py:1-19`), so projecting it yields a pack whose closure is non-trivial with no new fixture authored. The forge-source e2e fixture is `tests/fixtures/forge_workdir/` (copied to tmp by conftest because forge operations write into it, `conftest.py:26-36`).
10. **The osrlib release rides an established loop, and the next cut already has content.** The 1.3.0 stocking release is the precedent end to end: a leaf `crawl/` module importing from both `core` and `crawl/dungeon`, developed as plan-PR then implementation-PR under osrlib's own `AGENTS.md`, one changelog bullet, docstring-only docs via `gen_api_reference`'s `__all__` walk, released by editing `pyproject.toml` and running `uv lock` and nothing else. Adding a kind and models touches none of the three compatibility fences (`osrlib AGENTS.md:32`) — a minor bump, 1.4.0, no `SCHEMA_VERSION` bump — and `[Unreleased]` already holds four bullets, so the pack release joins that section. Two gates a new module trips: `test_public_surface.py` (exact `__all__` parity) and `test_docs_examples.py` (module docstrings' python blocks execute). One housekeeping defect rides along: `CHANGELOG.md:65-69` never got its `[1.3.0]` link line and `[Unreleased]` still compares `v1.2.1...HEAD` — the pack PR fixes it in passing, in the repo that owns it.
11. **Playwright and HTML5 drag are an uneasy pair, and the answer is coverage, not exemptions.** Playwright's `dragAndDrop` drives Chromium's native drag events, but HTML5 DnD under automation is historically the flakiest gesture family it covers — and the spec independently requires a click-to-place fallback for keyboards, trackpads, and assistive tech. Both paths are e2e-covered and both are held to the suite's existing determinism bar — no retry annotations exist in the suite and none arrive with this phase. Click-to-place carries the milestone spec because it is the path that must work even where drag cannot; a dedicated spec proves the drag gesture itself. If Chromium's native drag genuinely cannot be driven deterministically, that surfaces as an implementation finding and the plan amends on the branch — the standing rule — rather than being pre-excused here.
12. **Phase 10's conventions apply in full: a new surface means a new guide page, new shots, and re-captured old ones.** The published guides gain a content-library page, and phase 11 changes one surface in the committed shot set — the import dialog (`import-dialog` shot; the replace-mode `window.confirm` at `import-dialog.tsx:160-171` becomes the stash offer), which re-captures in the same PR (`AGENTS.md`'s convention) — while the clear-content dialog, also changed, has no committed shot today and enters the set as a new slug. `scripts/check_screenshots.py` holds docs↔files↔harness in all three directions, and every new shot asserts its state before capturing.

## Scope

In scope:

- The osrlib growth — `ContentPack`, `PackSection`, `ContentPackEntry`, `PackFinding`, `validate_content_pack`, the `content_pack` kind with `to_document`/`from_document` and the documented accepted-older, re-stamp-on-write posture — an additive minor release (1.4.0) developed under osrlib's own loop; the editor consumes it
- `library.py` — the pack projection (adventure → pack, closure included), the derived-source open across its three branches, and the stash capture
- Routes: `POST /api/sources/open`, `POST /api/projects/{id}/library/stash`, `POST /api/projects/{id}/library/stash/open`; the library error vocabulary
- Sidecar growth: the stash (packs, counter), the copies map, the `record_copy` and `remove_stash_pack` patches, and the cascade join with its parity suites
- Frontend: the library panel (sources, stash, badges), drag-and-drop with click-to-place, the drop mapper with collision prompts and template closure, wandering-table copy, and the stash offers replacing both destructive confirms
- Type generation growth, the content-library guide page with its screenshots, the `import-dialog` re-capture, README and CHANGELOG updates
- Test suites (pytest, vitest, Playwright) green in CI with zero network; the milestone's deterministic half in Playwright and its real half recorded in the PR

Out of scope (each with where it goes): **Standalone pack files** — saving the stash or a selection as a stamped file, opening pack files in the panel, monsters-only packs with one-click template adoption, and the `POST /projects/{id}/packs/save` route (phase 12; the model, the `habitat` field on the source response, and the identity scheme are designed here so phase 12 adds a branch, not a redesign). **A pack editor** — composing packs without a host adventure (spec future extensions; the panel stays read-only by spec). **On-map used badges** — the spec places used/unused badges on the palette; the map's marker channel stays error/warning (`render.ts:59-61`), and widening it waits for a feature that needs it. **Stashing level-scope features** — a deliberate decision recorded in work item 4, not a deferral: the pack holds rooms and wandering tables by the spec's own model, level-scope features are cell-bound by validation rule (`adventure.py:193-195`) and so geometry-bound by nature, and undo remains the way back for them exactly as it is for the geometry itself. **Panel auto-refresh** — a derived pack is a snapshot as of its open; the panel offers manual re-open and nothing re-syncs (the spec's provenance posture), so live refresh waits for evidence anyone wants it. **Kind-aware `MIGRATIONS`** — explicitly deferred by the spec to the osrlib release that first ships a payload-breaking pack change.

## Work items

### 1. The osrlib `content_pack` release

A new module `src/osrlib/crawl/content_pack.py` (a leaf beside `crawl/stocking.py` — it imports content models from `crawl/dungeon.py` and `MonsterTemplate` from `core/monsters.py`, so it cannot live in `core`), developed and reviewed under osrlib's own `AGENTS.md` loop, released as 1.4.0:

- **`ContentPackEntry`** (frozen): `id: str` (min length 1), `name: str = ""`, `description: str = ""`, `encounter: KeyedEncounter | None = None`, `trap: TrapSpec | None = None`, `treasure: AreaTreasureSpec | None = None`, `features: tuple[FeatureSpec, ...] = ()`. The entry is `AreaSpec` minus geometry, not a wrapper around it (research fact 4), and it restates the one coupling that would otherwise be lost: an entry trap must be `kind="room"`, mirroring `AreaSpec._trap_kind_matches`; the treasure-trap coupling needs no restatement because it lives on `FeatureSpec` itself.
- **`PackSection`** (frozen): `id: str` (min length 1), `label: str = ""`, `entries: tuple[ContentPackEntry, ...] = ()`, `wandering: WanderingSpec | None = None`. Sections exist because three consumers operate on a level grouping — the panel's level rows, wandering's level scope, and the stash's level capture — and making the grouping structural is what keeps it working when phase 12 mints entry ids that are no longer address-shaped; a stringly group-label convention would break exactly then. The pack remains "a set of entries" in the sense that matters: entry ids are unique pack-wide, so drops and provenance address entries by id alone and sections are presentation grouping plus the wandering slot.
- **`ContentPack`** (frozen): `id: str = ""`, `name: str = ""`, `description: str = ""`, `author: str = ""`, `sections: tuple[PackSection, ...] = ()`, `monsters: tuple[MonsterTemplate, ...] = ()`. Model validators enforce pack-wide entry-id uniqueness, section-id uniqueness, and monster-id uniqueness (the `MonsterCatalog` rule, `monsters.py:418-423`) — identity is what drops and provenance stand on, so a pack that breaks it refuses to load rather than lingering as a diagnostic. `id` defaults empty because derived packs never persist and take their identity from their source path; the stash and phase 12 mint real ids into it.
- **The kind**: `CONTENT_PACK_KIND = "content_pack"`, with `ContentPack.to_document()` → `stamp_document(CONTENT_PACK_KIND, self.model_dump(mode="json"))` and `ContentPack.from_document(document)` → `check_document` then `model_validate`, `ValueError` wrapped into `ContentValidationError` — the character/party pattern verbatim (research fact 2). The docstring documents the acceptance rules as the pack's own: an older `schema_version` is accepted on load; a newer one fails with `SaveVersionError`; any write re-stamps at current versions. No `MIGRATIONS` change — the deferral the spec pins, and the character/party precedent proves it defers cleanly.
- **`validate_content_pack(pack, monsters, equipment) -> tuple[PackFinding, ...]`** with `PackFinding` (frozen): `code: str` (dotted snake_case, the `Rejection` discipline), `message: str`, `entry_id: str | None`. Findings are the self-containment checks the spec names and nothing more: an encounter line or wandering row whose `template_id`/monster id resolves against neither `pack.monsters` nor the shipped catalog; a feature `item_ids` entry unknown to the equipment catalog. Returning findings instead of raising is research fact 3's argument made code — the first consumer is a panel, and the editor must never grow a second string-parser. A caller wanting a gate checks for a non-empty result.
- Module `__all__` (the public-surface gate), a runnable docstring example (the docs-examples gate), one changelog bullet joining `[Unreleased]`, and the missing `[1.3.0]` link-block repair (research fact 10).
- Editor dependency: floor bump to `osrlib>=1.4,<2` in the implementation PR. If implementation outpaces the release, the interim is the recorded family posture — a `[tool.uv.sources]` pin at the merged commit, swapped for the plain range when 1.4.0 publishes (the phase 7 arrangement).

### 2. Projection and the source habitats

`src/osreditor/library.py` owns everything between osrlib's pack model and the routes:

- **`pack_from_adventure(adventure) -> ContentPack`** — pure. One section per dungeon/level in document order; one entry per area in key order. Section and entry ids are the **diagnostics address grammar** — `dungeon:main/level:2` and `dungeon:main/level:2/area:7`, the percent-encoded `kind:value` form `addresses.py` builds and `address.ts` mirrors — one grammar everywhere: it is the same grammar the copies map keys speak, both sides already have builders, and the encoding is what keeps a dungeon id containing `/` from rendering two sources' entry ids ambiguous (an unencoded slash-join would let a legal document collide with itself and trip the pack's uniqueness validator). `label` from the dungeon and level names. Entry `name`/`description` copied verbatim, `encounter`/`trap`/`treasure` carried when present, features carried with their **`cell` binding stripped to `None`** — a cell is geometry, geometry never copies, and a preserved binding would land on an unrelated or out-of-bounds cell in any target; the author re-binds by hand where it matters. A slide trap's embedded `TransitionSpec` is kept verbatim — the spec names it as legitimately arriving dangling, standard diagnostics posture. **Wandering participation has exactly one predicate**, defined here and shared by every consumer: `wandering_is_authored(spec)` — the spec differs from a default-constructed `WanderingSpec()` (frozen-model equality). `WanderingSpec` exists on every level with RAW defaults (`dungeon.py:471-482`), so "has a table" would silently drop an authored chance-only spec and "always" would offer every section a copy that overwrites a target with RAW defaults; differs-from-default is the honest authored test. The projection carries a section's `wandering` exactly when the predicate holds, the panel offers the copy affordance exactly then, and the fully-used computation counts the wandering entry exactly when the capture carried one. `monsters` is the closure: every template on `Adventure.monsters` whose id is referenced by any projected encounter or wandering row — referenced ids that are neither bundled nor shipped stay dangling and become panel findings, which is the honest record of a source that was already dangling.
- **`open_source(service, path) -> SourceState`** resolves the habitat and never writes to the source:
    - *The path is an open project* (`service.open_at`, research fact 7): project the working document directly — no disk read, revision-consistent, the document value read under the project lock. This branch is also how "this project" appears in its own panel.
    - *A native project*: `read_artifact` through the `ProjectStore` seam — the seam's first true second-project consumer — then `load_adventure` and project. Never a raw filesystem read. The geometry importer's `Path.read_bytes()` (`importers/project.py:58-61`) is not a violation of this rule but a different seam with a different nature, and the line is drawn here so nobody "fixes" the wrong side: importers are format converters over arbitrary user-chosen local files — a third-party importer can know nothing of the store, and a project directory is simply one file shape among its inputs, beside a Watabou JSON — while the library opens projects *as projects*, with the project layer's own classification and loading discipline, and therefore reads exactly where the project layer reads.
    - *A forge workdir*: `open_workdir_state` through the forge bridge — current-first, the rebuild-on-open posture project open pins, the writes being forge's own artifacts — then project the assembled adventure. An unassemblable workdir surfaces `ForgeWorkdirIncompleteError` with the first-incomplete-stage remedy, the same refusal as review.
    - Classification reuses `classify_artifact_names` (forge first, since a workdir also holds an assembled root `adventure.json`); anything else refuses with the existing project-open vocabulary. No `OpenProject` registers and nothing the editor owns persists — but the concurrency is pinned rather than waved off: the open-project check and a workdir-source assembly run under the same synchronization `get_or_open` uses to serialize project opens, so a source open and a project open of one workdir can never interleave two assemblies; and a workdir whose conversion is bound and running refuses the source open with the conversion-busy remedy — the same rule that keeps every other document act off an active workdir.
- **`SourceState`** (frozen): `identity: str`, `label: str`, `habitat: Literal["project", "stash"]` (phase 12 adds `"file"`), `pack: ContentPack`, `findings: tuple[PackFinding, ...]` from `validate_content_pack` over the shipped catalogs. Identity is pinned per habitat exactly as the spec assigns it: a derived pack's identity is the resolved absolute source path; a stash pack's is its minted id. The two can never collide — paths are absolute, stash ids are `stash-<n>`.
- **`stash_pack_for_level(adventure, dungeon_id, level_number, ...)`** — the level-scoped projection the stash act uses: one section (that level's rooms, plus its wandering entry when the authored predicate holds), the closure computed over that section alone, `id` from the stash counter and `name` the label, whose composition is pinned because it freezes into a pack and a screenshot: the dungeon's `name` when non-empty else its `id` (starter dungeons scaffold `name=""`, `projects.py:141-153`), the word `level` and the number, an em dash, and the UTC date as `YYYY-MM-DD` from the server clock — the provenance `created_at` precedent ("Mill dungeon level 2 — 2026-07-28").

### 3. Sidecar growth: the stash, the copies map, and the cascade join

`EditorSidecar` grows three additive fields (no version bump, the additive-only rule):

- **`stash: tuple[StashedPack, ...] = ()`** — `StashedPack` (frozen): `pack_id: str`, `label: str`, `created_at: str`, `document: JsonValue` (the stamped envelope, `ContentPack.to_document()`'s output verbatim). The wrapper duplicates `pack_id` and `label` out of the envelope deliberately: the panel lists stash packs without parsing every stamped payload, and a pack a newer engine stamped — which `from_document` must refuse — can still be *named* in the listing with the upgrade remedy instead of vanishing. Drift is impossible because stash packs are immutable: created by the stash act, deleted by the patch, never edited. This is the sidecar's one content-bearing field, the owner-sanctioned posture change the spec records. The whole sidecar rides every op result today (`ops.py:740`); stash packs are level-sized projections over localhost JSON, so the added weight is accepted and noted rather than engineered around.
- **`stash_counter: int = 0`** — mints `stash-<n>` monotonically. Next-free minting would be wrong here: copy records outlive pack deletion by design ("the copies are complete, and nothing ever re-syncs"), so a re-minted `stash-1` would inherit a dead pack's badges. A boring counter is the correctness.
- **`copies: dict[str, tuple[CopyRecord, ...]] = {}`** — addressed map #3, keyed by *target* address (area address for room drops, level address for wandering copies; monster address joins in phase 12 for template adoption). `CopyRecord` (frozen): `pack_identity: str`, `pack_entry_id: str` — the entry id for a room drop, the section id for a wandering copy. Records are append-with-dedupe (an identical triple never doubles) and their *content* never rides the undo stack — only their keys cascade, the notes contract verbatim. **Undoing a drop does not unearn the badge**, pinned and surfaced in the panel's copy: a copy record is a record of the copy act, "used means at least once," and the spec's own posture for the stash's harmless duplicate applies here too. On area removal records go dormant, not deleted — the notes rule.
- **The cascade join**: `copies` keys enter `_remap_sidecar_keys`' union walk beside `notes` and `streams`, ride the same `HistoryEntry.key_remap` replay, and the parity suite grows to assert three-way key-for-key parity across every remap rule and across undo/redo of every re-keying op — the two-map suite's cases extended, not duplicated (research fact 5).
- **Patches**: `RecordCopy` (`action: "record_copy"`, `address`, `pack_identity`, `pack_entry_id`) and `RemoveStashPack` (`action: "remove_stash_pack"`, `pack_id`) join the discriminated union. Both ride the unguarded sidecar channel: copy records are annotation by nature, and stash deletion stays on the unguarded channel by the same owner sanction the spec records — the 409 discipline protects the deliverable, the stash is a recovery buffer, and git remains the cross-session net. The frontend fronts `remove_stash_pack` with a destructive-action confirm naming what is discarded (red, the reserved palette).

### 4. The stash act and the library routes

- **`POST /api/projects/{project_id}/library/stash`** — `StashRequest{revision, dungeon_id, level_number}` → the compound act on the `apply_stock` template (research fact 6): one lock acquisition; the stale-revision 409 *before* any capture, so a stash is always computed against the revision the destructive batch will run at; resolve the level (missing targets reuse `OpTargetNotFoundError`); `stash_pack_for_level`; mint the id from the counter; append the `StashedPack`; `persist_sidecar` in the same critical section; return the updated sidecar. The client then posts the destructive batch as its ordinary guarded self, sequenced through the store's single-flight queue. The two acts are deliberately not one: the stash is sidecar, the batch is document, and every failure mode lands on a posture the spec already names — a batch that 409s after a stash leaves an intact level plus a stash pack, the same "harmless duplicate, not a conflict, and deletable" as undoing the replace. **What the capture holds is the level's rooms and wandering table — not its level-scope features**, the spec's own enumeration: they are cell-bound by validation rule and so geometry-bound by nature, the pack model deliberately has no slot for them, and undo is the way back for them exactly as for the geometry. The stash-offer dialogs say so in their tally.
- **`POST /api/sources/open`** — body reuses the `_AbsolutePathRequest` shape (tilde-expanded, absolute); response is `SourceState`. Stateless: each open returns the pack, the panel holds it client-side, re-opening refreshes.
- **`POST /api/projects/{project_id}/library/stash/open`** — `{pack_id}` → the same `SourceState` shape (`habitat: "stash"`), produced by vetting the stored envelope server-side: `ContentPack.from_document` under the accepted-older rule, `validate_content_pack` findings included. A newer-engine pack maps to the existing schema-newer error with the upgrade remedy; an unknown id is 404 `stash_pack_not_found`. Routing every habitat through one response shape is what makes the panel never care where a pack came from — the spec's sentence, made a type.
- Every new route declares the auth dependency; `test_every_api_route_resolves_the_auth_dependency` enforces it for free.

### 5. Errors and type generation

- New errors: `StashPackNotFoundError` → 404 `stash_pack_not_found`. - **The stash list**: every `StashedPack` from the sidecar — label, date, fully-used state — with open (the stash-open route), and delete behind the destructive confirm naming the pack and its entry count. - **Pack contents**: sections as level rows (label, wandering-copy affordance exactly when the section carries a wandering entry — the authored predicate again, one test everywhere — and the used badge), entries as rows with name, kind glyphs for what the entry carries, and the used badge — computed client-side by filtering `sidecar.copies` for this pack's identity. Pack findings from the open response render at the top of the pack, the diagnostics posture: visible, never blocking.
- **Placement affordances**: every entry row is an HTML5 drag source and a click-to-arm button, and the mode arbitration with the map's tool system is pinned here rather than left to invention. Arming and the modal tools are mutually exclusive: arming an entry displaces the active tool's claim on the primary click, and selecting a map tool disarms — there is never a click both would claim. While armed, hover highlights the area under the cursor exactly as drag-over does; a click on an area places the entry and disarms (one placement per arm — repeats are what drag serves, and re-arming is one click); a click anywhere else — corridor, empty cell, off-grid — is a no-op that stays armed, because a missed click must not destroy the aim. Drags are untouched: panning works while armed. Escape, closing the panel, or closing the pack disarms. The armed state is panel state with render-time invalidation — the `cardIntent` pattern, not an effect.
- **Per-pack collision memory** lives on the panel keyed by pack identity — panel state, never persisted, dying when the pack closes — matching the spec's "remembered while that pack stays open in the panel." Each kind's choice is remembered as it is made; a later drop colliding on a kind not yet chosen prompts for that kind only.

### 7. The drop mapper, collisions, and placement

`src/lib/library-drop.ts`, the import-mapping discipline exactly — pure functions, committed through the store's builder form as one ordinary op batch:

- **`dropCollisions(entry, area)`** — the pure collision predicate: a single-slot kind collides when the entry carries it and the target area already has it. Carried means non-empty for prose (`name`, `description` — projection preserves source strings, so empty means the source had none) and non-null/non-empty for `encounter`, `trap`, `treasure`. Features never collide — the plural kind always appends.
- **`dropOps(entry, pack, document, target, choices)`** — emits, for carried kinds only, honoring per-kind replace-or-keep: `SetAreaField` name/description, `SetEncounter`, `SetTrap`, `SetTreasure`, then `AddFeature` per feature with ids re-minted through `nextFreeFeatureKey` sequentially (each mint joins the taken set before the next, so one batch never collides with itself). Merge is the default posture, not a mode: a kept kind emits nothing, and a trap-only entry dropped on a stocked room touches only the trap slot.
- **Template closure**, computed inside the mapper over the entry's encounter references (and the section's wandering rows for a wandering copy). Resolution order per referenced pack template, pinned because the repeat-drop case would otherwise mint a clone per drop: (1) the reference resolves to a shipped-catalog template the pack does not shadow with a differing definition — no op, the id stands everywhere; (2) a target bundled template with the same id and an identical definition — reuse, no op; (3) any target bundled template structurally identical *apart from `id`* — rewrite the dropped reference to that twin, no op: this is what keeps thirty drops of one shadowed template at one clone total, because the first drop's `orc-1` is every later drop's twin; (4) no id conflict and no twin — `AddMonsterTemplate` as carried; (5) id taken with a differing definition and no twin — re-mint through `cloneId` and rewrite the dropped reference. Identity is deep structural equality on the serialized template (id excluded only in the twin test) — both sides arrive as server-serialized JSON with pydantic's stable field order, but the comparison is structural, never a string compare. In a forge-backed target the mapper changes nothing: a closure-bearing batch blocks whole at `ensure_forge_supported` before any side effect and surfaces the detach offer through the existing blocked-op dialog (research fact 1), while a drop that resolves entirely against shipped or already-carried templates translates clean.
- **The collision dialog** fires only for colliding kinds with no remembered choice: one dialog naming the kinds with per-kind replace-or-keep, replace preselected, and the choices recorded into the pack's panel memory. The OPD case is the acceptance test: thirty areas carrying Watabou note text prompt once.
- **Wandering copy** is the level row's affordance: a `SetWandering` batch with the same closure treatment, target address the level. In a forge-backed target it blocks in place through the same server path.
- **Provenance**: after a successful drop or wandering copy, the store chains a `record_copy` patch (target address, pack identity, entry or section id) onto the same single-flight queue. A crash between batch and patch costs a badge, not content — provenance is a convenience record, and re-dropping is allowed.
- **Drop targets are existing areas only** — the wrapper-div handlers resolve through hit-test + `areaAt` and refuse anywhere else; corridors are unkeyed floor and creating areas stays the area tool's job.
